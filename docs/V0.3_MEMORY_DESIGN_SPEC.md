# Human-in-the-Loop Memory Policy

Memory belongs to Teacher.

Teacher must always remain in control of long-term memory.

The system should be designed so that future versions can:

- Show stored memories.
- Edit memories.
- Delete memories.
- Forget selected memories.
- Clear all memories.

Even if these features are not implemented in v0.3,

the architecture must support them naturally.

Arona should never become an uncontrollable memory system.

---

# Objective

Transform Arona from:

LLM

↓

Conversation

into

LLM

+

Long-term Memory

↓

AI Companion

Memory should improve continuity between conversations.

Memory is NOT chat history.

---

# Extremely Important

Conversation and Memory are two completely different concepts.

Never merge them.

Conversation:

Temporary.

Current chat session.

Can be cleared.

Memory:

Persistent.

Cross-session.

Lives inside SQLite.

Survives application restarts.

---

# Philosophy

Arona should remember things about Teacher.

Arona should NOT remember every sentence.

Memory stores knowledge.

Conversation stores dialogue.

# Memory Lifetime

Memory is permanent until:

Teacher deletes it

Future memory management

# AICompanion

AICompanion becomes responsible for coordinating:

Conversation

MemoryManager

Gemini

PromptBuilder

---

# Memory Injection

Every request should NOT inject the entire database.

Instead:

Load only relevant memories.

Future implementations may become smarter.

For now:

Limit memory count.

Example:

Top 10 memories.

Avoid extremely long prompts.

---

# Memory Categories

Each memory should have a category.

Suggested categories:

Preference

Relationship

Identity

Project

Schedule

General

Example:

Preference

Teacher likes coffee.

Relationship

Teacher prefers to be called Teacher.

Project

Teacher is building an AI Companion.

# Metadata

Each memory should contain:

id

category

content

created_at

updated_at

Optional future fields:

importance

last_access

access_count

Do not implement unnecessary fields yet.

---

# Memory Creation

Memory should NEVER be created automatically for every message.

Only create memories when information is useful long-term.

Examples:

"My favorite color is blue."

Good.

"I ate fried rice today."

Usually ignore.

---

# Memory Decision

Claude should design a clean decision layer.

Avoid hardcoding hundreds of if statements.

The system should remain extensible.

---

# Memory Editing

Future versions should support:

Edit memory

Delete memory

List memory

Current version only needs architecture compatibility.

---

# Prompt Injection

PromptBuilder should remain unchanged.

Instead,

AICompanion should inject memory into Gemini before sending.

Flow:

PromptBuilder

↓

System Prompt

↓

Relevant Memories

↓

Conversation History

↓

Gemini

PromptBuilder should not know SQLite exists.

---

# GUI

GUI should remain completely unchanged.

The GUI should not know memory exists.

GUI still only calls:

reply = companion.chat(user_input)

Everything else happens internally.

---

# Performance

Avoid loading all memories.

Avoid rebuilding unnecessary prompts.

Avoid duplicate memories.

SQLite queries should remain simple.

---

# Duplicate Prevention

Avoid saving identical memories.

If:

Teacher likes coffee.

already exists,

Do not create another identical entry.

Instead:

Update timestamp if necessary.

---

# Logging

Continue using logger.

Log:

Memory created

Memory updated

Memory ignored

Memory loaded

Memory deleted

---

# Error Handling

Memory failures must never crash the application.

If SQLite fails,

Conversation should continue.

Gracefully degrade.
