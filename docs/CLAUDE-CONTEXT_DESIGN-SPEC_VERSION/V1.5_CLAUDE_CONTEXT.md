# Apa yang diminta (dari ChatGPT pemandu)

v1.5 = tambah **Vision Experience** (bikin Vision System v0.7 yang sudah ada
jadi benar-benar bisa dipakai & dipahami Teacher), bukan Vision System v2.
Guardrail dari pemandu:

- Vision existing v0.7 dipakai ulang, bukan dibuat ulang.
- ON/OFF wajib jelas bagi user.
- Manual Capture menjadi jalur utama.
- AUTO hanya boleh dibuat kalau arsitektur existing memang aman; kalau
  tidak, skip.
- Fresh `VisionContext` harus dipakai ulang agar tidak boros capture/API.
- Vision masuk ke Arona lewat `ContextBuilder` yang sudah ada.
- Tidak ada screenshot permanen.
- Tidak ada OCR, face recognition, webcam, image upload, atau video
  analysis.
- Tidak ada VisionManager v2, Plugin System, maupun Outfit System.

Setelah v1.5, semua 6 halaman sidebar (Chat/Memory/Voice/Avatar/Vision/
Settings) fungsional.

# Temuan penting dari inspeksi (`vision/vision.py`, `vision_context.py`, `vision_signals.py`, dkk)

Ini bukan asumsi — dikonfirmasi baca source langsung sebelum implementasi.
**Temuan #1 di bawah adalah alasan kenapa arsitektur ON/OFF v1.5 berbeda dari
yang biasanya dibayangkan orang (bukan toggle backend, murni GUI):**

1. **`Vision` class TIDAK PUNYA `enable()`/`disable()`/`is_enabled` sama
   sekali.** Digabung dengan fakta `main_gui.py` SELALU construct `Vision`
   dan SELALU pass ke `Companion` (tidak ada cabang kondisional apa pun) —
   ini persis Stop Condition #4 di spec (*"Enable/disable has no safe
   configuration contract"*). **Tapi ini tidak memicu STOP total**, karena
   ditemukan jalan aman: lihat temuan #2.
2. **Capture BARU (`Vision.refresh()`) HANYA PERNAH dipanggil lewat SATU
   jalur di seluruh aplikasi: `Companion.capture_vision()`, yang HANYA
   PERNAH dipanggil dari tombol GUI manual.** `Companion.chat()` TIDAK
   PERNAH memanggil `capture_vision()` — cuma memanggil
   `self._vision.get_context()` (baca cache, tidak pernah capture baru).
   Ini adalah **Capture Policy yang sudah ada sejak v0.7**, bukan sesuatu
   yang saya buat di v1.5. Konsekuensinya: **men-disable tombol "Capture
   Screen" saat toggle OFF sudah CUKUP untuk menjamin "tidak ada capture
   baru"** (Privacy Policy §7), tanpa perlu API enable/disable baru di
   `Vision`/`Companion` sama sekali. Ini keputusan arsitektural paling
   penting di v1.5 — kalau ada yang bertanya "kenapa Vision ON/OFF cuma
   state lokal GUI, bukan flag di backend", jawabannya ada di sini.
3. **`Vision.get_context()` vs `Vision.refresh()` sudah persis
   mengimplementasikan Freshness Policy v0.7**: `get_context()` cuma return
   context kalau `is_fresh()` True (umur ≤ TTL), tidak pernah trigger
   capture baru, return `None` kalau stale/belum ada. `refresh()` selalu
   paksa capture+analyze baru. Vision GUI pakai `get_context()` untuk
   tampilan pasif (buka halaman = TIDAK capture), dan `refresh()` (lewat
   tombol "Capture Screen") untuk aksi eksplisit — pemetaan ini penting
   supaya §10 ("jangan capture kalau tidak perlu") benar-benar dipatuhi.
4. **Error handling SUDAH SEPENUHNYA diserap di layer `Vision`** —
   `Vision.refresh()` membungkus kegagalan capture (`except Exception:
   return self._current_context`), dan `Vision.analyze()` membungkus
   kegagalan analysis (`except Exception: self._current_context = None;
   return None`). Akibatnya: **dari sisi caller (`Companion.capture_vision()`
   dan GUI), TIDAK BISA dibedakan mana yang gagal** — capture atau analysis
   — keduanya sama-sama berakhir sebagai return value `None` atau context
   lama. Karena itu Vision GUI **sengaja hanya punya SATU pesan error
   generik** ("Vision capture failed. Please try again."), BUKAN dua pesan
   berbeda seperti di mockup spec §24 — menampilkan dua pesan berbeda akan
   berarti mengarang presisi diagnostik yang tidak tersedia di backend.
5. **`Vision.refresh()` = network-bound (panggil Gemini Vision lewat
   `ImageAnalyzer.analyze()`)** — blocking call sungguhan, sekelas
   `Companion.chat()`. Tidak ada worker existing yang cocok (ChatWorker
   khusus chat, VoiceWorker khusus voice pipeline), jadi dibuat
   `ui/vision_worker.py` baru — **dibenarkan eksplisit oleh File Change
   Policy §27** ("only if inspection proves it necessary" — sudah
   terbukti lewat temuan ini), mengikuti pola persis `ChatWorker`.
6. **AUTO mode: tidak ada scheduler yang aman untuk direuse.** `Vision`
   tidak punya timer/polling internal apa pun. Scheduler yang ada di project
   (`IdleScheduler` milik Avatar, `RoutineScheduler` milik Routine)
   masing-masing terikat erat ke domainnya sendiri — menghubungkannya ke
   Vision akan jadi arsitektur baru yang eksplisit dilarang §20. **AUTO
   mode di-skip total dari v1.5**, sesuai "If AUTO is unsafe, omit AUTO"
   (Final Rules §34).
7. **`vision_signals.py` memang ada** (`matches_presentation()`,
   `matches_focused_work()`) — dipakai bersama `routine_rules.py` dan
   `initiative_rules.py` untuk deteksi suppression. **Tidak disentuh sama
   sekali di v1.5** — Vision GUI tidak perlu berinteraksi dengan file ini,
   Routine/Initiative tetap membacanya lewat jalur yang sudah ada.
8. **Companion/ContextBuilder sudah 100% mendukung alur "Vision → chat
   reply" tanpa perlu diubah sama sekali.** `Companion.chat()` sudah
   memanggil `self._vision.get_context()` di awal dan menyuntikkannya ke
   `ContextBuilder.build(..., vision_context=vision_context, ...)`, yang
   sudah punya `_format_vision()` sejak v0.7. **Zero backend changes** untuk
   membuat Vision benar-benar memengaruhi balasan Arona — ini murni soal
   mengekspos tombol capture yang sudah terhubung ke pipeline yang sudah
   ada.

# Yang sudah diimplementasikan

## 1. `ui/vision_worker.py` — BARU

`VisionWorker(QThread)` — pola persis `ChatWorker`:
- `result_ready = Signal(object)` — emit `Optional[VisionContext]`.
- `error_occurred = Signal(str)` — defensif saja (`Companion.capture_vision()`
  pada praktiknya tidak pernah raise, sudah dibungkus penuh di layer
  `Vision`, lihat temuan #4), tapi try/except tetap ada mengikuti gaya
  worker lain di project.
- `run()` cuma memanggil `self._companion.capture_vision()`, tidak ada
  logic Vision apa pun di sini.

## 2. `ui/vision.py` — BARU

`VisionPage(QWidget)`:
- `self._enabled: bool = True` — **state GUI-only, in-memory, TIDAK
  PERSISTEN**, default ON (sama seperti perilaku Vision sebelum v1.5 yang
  selalu aktif — tidak ada regresi UX).
- Status: `👁 Vision: ● ON` / `👁 Vision: ○ OFF` — indikator selalu terlihat,
  BUKAN checkbox tersembunyi di Settings (sesuai §7 eksplisit).
- Tombol toggle "Turn Vision OFF"/"Turn Vision ON" — saat OFF, tombol
  "Capture Screen" **disabled**, kartu Freshness/Context ditampilkan
  sebagai "Vision is off. No capture will be taken." / "—".
- "Mode: Manual (only mode currently available)" — Read Only text, BUKAN
  dropdown seperti mockup (AUTO tidak pernah ada untuk dipilih, dropdown
  akan jadi fiktif — sama treatment dengan Theme di v1.4).
- Tombol "📷 Capture Screen" — trigger `VisionWorker`, disabled selama
  in-flight, re-enabled setelah hasil/error.
- Kartu Freshness — `Captured: {tanggal, WIB}`, `Age: {detik}`,
  `TTL: {detik}`, `Fresh: YES/NO` — SEMUA dari field asli
  `VisionContext` (`.timestamp`, `.age_seconds()`, `.ttl`, `.is_fresh()`),
  tidak ada field yang dikarang.
- Kartu Vision Context — `Application: {...}` (kalau ada) + `.summary` teks
  asli dari Gemini Vision, ditampilkan apa adanya. **TIDAK ADA screenshot
  preview** (§19 eksplisit — `Vision` tidak expose bytes gambar dengan aman
  untuk GUI, jadi tidak ditampilkan).
- `showEvent()` cuma baca `current_vision_context()` (cache, no-capture) —
  membuka halaman TIDAK PERNAH memicu screenshot baru.
- Timestamp ditampilkan dalam **Asia/Jakarta** (`ZoneInfo`), konsisten
  dengan konvensi `ContextBuilder._format_time()` yang sudah ada.

# Vision → Arona: alur nyata yang sudah terverifikasi (bukan cuma diklaim)

```
1. Teacher buka halaman Vision → klik "Capture Screen"
        ↓
   Companion.capture_vision() → Vision.refresh()
   → screenshot (MssScreenCapture) + Gemini Vision analyze (ImageAnalyzer)
   → VisionContext baru tersimpan di dalam Vision (Companion's instance)

2. Teacher pindah ke Chat (atau Voice), kirim pesan apa saja
        ↓
   Companion.chat() memanggil self._vision.get_context() di awal
        ↓
   Kalau context masih fresh (age ≤ TTL, default 30 detik):
   disuntikkan ke ContextBuilder.build(..., vision_context=...)
   → Gemini menerima info visual sebagai bagian dari Ephemeral Context
   → Arona bisa merespons natural sesuai apa yang "terlihat"
```

Kalau context sudah kadaluarsa (>TTL) atau belum pernah capture sama sekali,
`get_context()` return `None`, chat tetap jalan normal tanpa info visual —
tidak error, cuma tidak ada konteks visual.

Ini berlaku sama untuk chat lewat teks maupun voice (`VoiceManager.
stop_recording_and_respond()` juga memanggil `Companion.chat()` yang sama).

# Deviasi dari mockup (disengaja, didokumentasikan)

1. **ON/OFF adalah state GUI-only, TIDAK PERSISTEN** — bukan pengawasan
   yang kurang, tapi karena `Vision` memang tidak punya kontrak
   enable/disable maupun persistence apa pun (§21/§32: *"Do not invent
   persistence"*).
2. **Satu pesan error generik**, bukan dua ("Unable to capture the
   screen" vs "Vision analysis failed" di mockup §24) — backend sudah
   menggabungkan kedua kegagalan itu jadi tidak bisa dibedakan dari GUI.
3. **"Mode: Manual" ditampilkan sebagai teks statis**, bukan dropdown —
   AUTO tidak pernah ada untuk dipilih.
4. **Tidak ada screenshot preview** — `Vision` tidak expose bytes gambar ke
   pemanggil dengan cara yang aman untuk ditampilkan (`_last_captured_image`
   itu private attribute, dan menampilkannya berarti keputusan penyimpanan/
   privacy baru yang di luar scope).

# Known limitation (bukan bug, konsekuensi dari desain yang disengaja)

- **Toggle OFF tidak menghapus `VisionContext` yang masih fresh dari
  capture sebelumnya di dalam `Companion`.** Kalau Teacher capture, lalu
  toggle OFF dalam beberapa detik, lalu langsung chat — `Companion.chat()`
  (tidak disentuh v1.5) tetap bisa memakai context lama itu SEKALI lagi
  lewat `get_context()`-nya sendiri, karena `Companion` tidak tahu apa-apa
  soal toggle GUI ini. Ini bukan regresi — TTL default cuma 30 detik jadi
  window eksposur ini sangat pendek dan otomatis hilang sendiri (Freshness
  Policy v0.7). Memperbaikinya sepenuhnya butuh mengubah `companion.py`
  (backend frozen) supaya sadar akan toggle GUI — di luar scope minimal
  v1.5, butuh diskusi eksplisit kalau mau diperketat.
- Kalau Arona ternyata tidak menyinggung konteks visual sama sekali di
  balasannya walau capture-nya fresh dan berhasil, itu **soal bagaimana
  `prompts/system_rules.txt`/personality menangani Ephemeral Context
  tambahan** (Gemini yang memutuskan kalimat, bukan kode) — bukan soal
  pipeline teknis Vision GUI yang salah. Di luar scope teknis yang
  disentuh v1.5.

# Instruksi untuk sesi Claude berikutnya

1. v1.5 Vision GUI **sudah diimplementasikan**, tapi confirm dulu ke user
   apakah sudah dijalankan & dites di environment asli sebelum menganggap
   statusnya final seperti v1.1-v1.4.
2. **Kalau user melaporkan Arona tidak pernah menyinggung konteks visual**:
   cek DULU apakah capture-nya benar-benar berhasil (buka halaman Vision,
   lihat kartu Freshness — `Fresh: YES` dan ada isi di kartu Context?).
   Kalau capture sukses tapi Arona tetap tidak menyinggungnya, itu ranah
   prompt/personality (`prompts/system_rules.txt` dkk), BUKAN bug di
   pipeline Vision GUI — jangan buru-buru ubah `vision_worker.py`/
   `vision.py` untuk masalah yang sebenarnya ada di prompt.
3. **Kalau user minta toggle OFF benar-benar memblokir context lama juga**
   (menutup known limitation di atas): itu butuh mengubah `companion.py`
   (backend frozen) supaya `chat()` sadar akan status enable/disable —
   **wajib didiskusikan eksplisit sebelum eksekusi**, bukan dianggap
   sebagai perbaikan kecil.
4. **Kalau user minta AUTO mode**: tidak ada scheduler aman untuk direuse
   saat ini. Menambahkannya berarti membangun scheduler architecture baru
   yang eksplisit dilarang di v1.5 — treat sebagai keputusan arsitektur
   v1.6+ yang butuh spec terpisah, bukan ekstensi kecil dari v1.5.
5. **Kalau user minta screenshot preview di GUI**: `Vision` tidak expose
   image bytes dengan aman untuk GUI saat ini (`_last_captured_image`
   private). Ini juga butuh keputusan privacy/penyimpanan baru — diskusikan
   dulu, jangan asumsikan aman untuk langsung ditambahkan.
6. **JANGAN PERNAH** membuat instance `Vision`/`ScreenCapture`/
   `ImageAnalyzer` baru di `ui/`. Semua halaman yang butuh Vision HARUS
   reuse `self._companion` yang sama dari `MainWindow` (yang sudah
   membungkus satu instance `Vision` yang benar sejak `main_gui.py`).
7. **JANGAN PERNAH** menampilkan/menyimpan/mencatat isi gambar (bytes,
   base64, path file screenshot permanen) ke log, Developer export, atau
   penyimpanan apa pun. Hanya teks deskripsi (`summary`/`application`) dan
   metadata (`timestamp`/`age`/`ttl`/`is_fresh`) yang boleh ditampilkan.
8. Arsitektur v1.0 (Architecture Freeze Policy) **masih berlaku** untuk
   semua subsystem di luar GUI. `Companion` tetap satu-satunya orchestrator,
   `ContextBuilder` tetap satu-satunya titik rakit runtime context.
9. Pola yang established sepanjang v1.1-v1.5: reuse manager/service instance
   yang sama lewat constructor injection, `QStackedWidget` untuk page
   switching, append-only ke `theme.py`, worker baru HANYA kalau terbukti
   perlu lewat inspeksi (network-bound call), dan **kalau backend sudah
   menggabungkan/menyembunyikan detail kegagalan, GUI tidak boleh
   mengarang presisi yang tidak ada**.
10. User komunikasi Bahasa Indonesia, kode/komentar teknis boleh Inggris.
