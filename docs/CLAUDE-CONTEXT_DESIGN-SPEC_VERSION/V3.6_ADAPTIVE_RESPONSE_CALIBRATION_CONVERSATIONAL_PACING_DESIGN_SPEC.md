# V3.6 — Adaptive Response Calibration & Conversational Pacing

## 0. Milestone Identity

**Version:** v3.6  
**Name:** Adaptive Response Calibration & Conversational Pacing  
**Status:** PLANNED  
**Previous milestone:** v3.5 — Temporal Awareness & Task Continuity  
**Primary goal:** Improve how Arona adapts the shape, depth, pacing, and interaction style of her responses to the current conversational situation without introducing a second reasoning system, response planner, task manager, or provider-specific behavior.

---

# 1. Why V3.6

By v3.5, Arona already has increasingly strong contextual evidence:

```text
v3.2 → Memory Quality
v3.3 → Contextual Recall
v3.4 → Memory Relevance Ranking
v3.5 → Temporal Awareness & Task Continuity
```

The remaining problem is increasingly:

> Given what Teacher is saying right now, what shape should Arona's response take?

Examples:

```text
Teacher: "error di auth nih"
→ direct, useful, not unnecessarily long

Teacher: "jelasin kenapa JWT bisa expired"
→ explanatory, potentially more detailed

Teacher: "aku capek banget debugging dari tadi"
→ acknowledge naturally instead of dumping a long technical explanation

Teacher: "lanjut yang tadi"
→ continuation-oriented response

Teacher: "sudah selesai backend-nya"
→ acknowledge completion instead of continuing to troubleshoot
```

V3.6 therefore introduces **response calibration signals**, not a second response-generation system.

---

# 2. Core Principle

V3.6 provides **conversation-shape evidence and explicit user preference cues**.

The existing LLM remains responsible for:

- interpreting the evidence
- deciding what the user wants
- choosing wording
- generating the final response
- preserving Arona's persona
- handling ambiguity

The application may detect explicit signals such as:

```text
"singkat aja"
"langsung jawab"
"jelasin detail"
"pelan-pelan"
"jangan panjang"
```

and lightweight conversational forms such as:

```text
question
request
problem_report
progress_update
completion_statement
casual_statement
acknowledgement
reference_followup
```

The application must NOT directly generate or force the final response.

# 4. Hard Boundaries

## 4.1 No Second LLM

Do NOT introduce:

```text
response planner LLM
tone classifier LLM
length classifier LLM
emotion classifier LLM
```

The normal conversational LLM remains the only generative intelligence.

## 4.2 No Response Template Engine

Do NOT convert response generation into rigid templates such as:

```text
if problem:
    output troubleshooting template
```

V3.6 provides guidance/evidence, not fixed answer templates.

## 4.3 No New Personality System

Do not redesign:

```text
prompts/personality.txt
prompts/speaking_style.txt
```

unless Phase 0 identifies a concrete regression.

## 4.4 No Persistent Response Mode

Do NOT create:

```text
current_response_mode
user_tone_state
preferred_length_state
```

as a new persistent subsystem.

Explicit long-term preferences may still use the existing MemoryExtractor when they genuinely qualify under existing rules.

## 4.5 No Task System

Do NOT create:

```text
TaskManager
ResponseTask
ConversationTask
Planner
```

## 4.6 No Provider-Specific Behavior

No new:

```python
if provider == "local":
```

or equivalent provider-specific response calibration.

## 4.7 No New Database

Do not add:

- another SQLite database
- response preference tables
- conversation mode tables

## 4.8 No Parallel Conversation History

`Conversation` remains the single process-lifetime history.

# 6. Phase 1 — Explicit User Pacing Cues

Highest priority should go to explicit instructions from Teacher.

### Concise cues

```text
singkat aja
yang singkat
jawab pendek
jangan panjang
langsung jawab
langsung aja
to the point
```

### Detailed cues

```text
jelasin detail
jelaskan secara lengkap
detail dong
jelasin pelan-pelan
bahas lengkap
lebih rinci
```

### Step-by-step cues

```text
satu-satu
step by step
langkah demi langkah
pelan-pelan
dari awal
```

### No-overexplaining cues

```text
nggak usah panjang
ga usah panjang
jangan terlalu panjang
langsung inti
```

Detection must be conservative.

It may report something such as:

```text
response_preference = concise
```

but must not infer:

```text
Teacher always prefers short answers
```

from one sentence.

```text

```

# 8. Phase 3 — Response Depth Guidance

Use explicit evidence for:

```text
concise
normal
detailed
step_by_step
```

Default remains:

```text
normal
```

No explicit cue = no forced response-length change.

Example:

```text
Teacher:
"jelasin detail kenapa JWT expired"

Calibration:
depth = detailed
form = request
```

Without an explicit depth request:

```text
Teacher:
"kenapa JWT expired?"

Calibration:
depth = normal
form = question
```

When multiple calibration cues appear, explicit Teacher instructions should dominate inferred conversational form.

# 12. Phase 7 — Contradictory Explicit Cues

Handle contradictory cues conservatively.

Example:

```text
"jelasin detail tapi singkat aja"
```

The application should preserve the evidence:

```text
explicit_depth_cues = ["detailed", "concise"]
```

Do NOT build a large conflict-resolution engine.

Let the LLM interpret the natural tradeoff.

# 15. Phase 10 — Explicit Preference vs Temporary Cue

Distinguish immediate instructions from stable preferences.

Example:

```text
"jawab singkat aja"
```

is a temporary conversational instruction.

It should not automatically become permanent memory.

A stable statement such as:

```text
"aku memang lebih suka jawaban singkat"
```

may be handled through the existing MemoryExtractor if the existing system determines it qualifies as a persistent preference.

V3.6 must not create a separate preference-storage path.

# 18. Phase 13 — Autonomous Safety


A previous Teacher instruction may remain part of ordinary conversation history, but it must not be treated as a newly issued instruction without evidence from a new Teacher message.

# 27. PASS / CONDITIONAL PASS / FAIL

- explicit cues work
- calibration evidence reaches the LLM correctly
- response behavior is naturally adaptive
- no rigid templates are introduced

```text

```

Hard failures include:

- second LLM/classifier introduced
- rigid response templates introduced
- application dictates exact response wording/length
- persistent response-mode state is added unnecessarily
- provider-specific calibration logic is introduced
- existing emotion/relationship systems are duplicated
- v3.3 reference behavior regresses
- v3.4 ranking behavior regresses

# 29. Final Milestone Intent

The intelligence progression becomes:

```text
v3.2
Memory Quality
"what is worth remembering?"
        ↓
v3.3
Contextual Recall
"what does this reference point toward?"
        ↓
v3.4
Memory Relevance Ranking
"which retrieved evidence matters most?"
        ↓
v3.5
Temporal Awareness
"what is happening in time / is it ongoing?"
        ↓
v3.6
Response Calibration
"given all that context, what response shape fits?"
        ↓
Existing LLM
"generate Arona's actual response"
```

Core principle:

> **V3.6 calibrates the conversation, not the answer. It gives the existing LLM truthful evidence about how Teacher is currently communicating, while leaving interpretation, wording, personality, and final response generation to the one existing conversational intelligence.**
