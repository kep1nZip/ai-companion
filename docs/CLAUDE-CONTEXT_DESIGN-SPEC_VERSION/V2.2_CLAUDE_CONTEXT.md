# v2.2 — Local Memory Extraction — STATUS: ✅ IMPLEMENTED (pending Teacher quality/runtime test)

## Ringkasan

`MemoryExtractor` sekarang **provider-agnostic**. Sebelumnya hardcode ke
`google.genai.Client` langsung; sekarang cuma menerima
`LanguageModelProvider` (abstraksi yang SAMA yang sudah dipakai Companion
untuk chat utama sejak v2.0) lewat dependency injection. Prompt ekstraksi
**tidak diubah satu karakter pun**.

```
v2.1 (sebelum)                          v2.2 (sesudah)

MemoryExtractor                         MemoryExtractor
  └─ google.genai.Client (hardcode)       └─ LanguageModelProvider (injected)
                                                ├─ GeminiProvider (default,
                                                │  temperature=0.0)
                                                └─ LocalProvider (opsional,
                                                   temperature=0.0, kalau
                                                   MEMORY_PROVIDER=local)
```

Async worker dari v2.1 (`ai/memory_worker.py`) **tidak disentuh sama
sekali** — task masih dijadwalkan lewat `Companion._schedule_memory_extraction`
→ `MemoryExtractionWorker.submit()`, satu thread, tidak blocking. v2.2 cuma
mengubah **APA** yang dijalankan task itu (provider mana), bukan **BAGAIMANA**
dijalankan.

## Keputusan Desain Penting (dan Kenapa)

### 1. `LanguageModelProvider` cukup — tidak perlu abstraksi baru

Spec eksplisit meminta saya menentukan: "Can `LanguageModelProvider` safely
represent a Memory Extraction request?" Jawaban saya: **ya**, dengan syarat
menggunakan **instance terpisah** dari provider chat utama.

`LanguageModelProvider.generate(contents) -> str` bentuknya sudah persis
cocok (satu `Content` role="user" berisi teks — ini SAMA PERSIS dengan cara
`MemoryExtractor` v2.1 sudah membentuk request-nya sendiri). Masalahnya
bukan bentuk kontrak, tapi bahwa `system_prompt` dan `temperature`
di-bake ke constructor provider (`LocalProvider`/`GeminiProvider`), bukan
per-panggilan — itu memang benar untuk chat (satu personality untuk seluruh
sesi), tapi salah kalau instance yang SAMA dipaksa dipakai untuk ekstraksi
(butuh system prompt & temperature yang total berbeda).

**Solusi:** bukan bikin abstraksi baru, tapi konstruksi **instance kedua**
provider yang sudah ada, dikonfigurasi khusus untuk ekstraksi. `LocalProvider`
sudah 100% mendukung ini tanpa perubahan (semua knob yang dibutuhkan sudah
jadi parameter constructor sejak v2.0). `GeminiProvider`/`GeminiClient`
**belum** — makanya saya tambah `temperature: Optional[float] = None`
(default `None` = perilaku lama, byte-identical, tidak breaking apa pun).

Hasil akhir: `MemoryExtractor` **tidak punya satu baris pun**
`if provider == "local"` — persis yang diminta spec §8. Percabangan
provider terjadi di LUAR `MemoryExtractor`, di titik konstruksi
(`Companion.__init__` / `main_gui.py`), sama seperti provider chat utama
sudah bekerja sejak v2.0.

### 2. Path Gemini extraction TETAP lewat `GeminiProvider`, bukan dipertahankan sebagai raw client terpisah

Ini pertimbangan risiko yang saya timbang secara sadar. Sebelumnya
`MemoryExtractor` punya `google.genai.Client` sendiri (terpisah dari
`GeminiProvider`/`GeminiClient` yang dipakai chat) — sudah **v2.1-verified
bekerja**. Saya bisa saja mempertahankannya utuh dan HANYA menambah cabang
Local secara terpisah (`if self._raw_client: ... else: self._provider.generate(...)`)
— ini lebih minim-risiko tapi melanggar §8 secara literal (masih ada
percabangan provider di dalam `MemoryExtractor`).

Saya pilih unifikasi penuh (Option A) karena:
- Perubahan ke `GeminiClient` murni **aditif** (parameter baru,
  default mempertahankan perilaku lama persis) — risiko regresi rendah,
  sudah diverifikasi lewat test (`temperature=None` → config Gemini tidak
  punya field `temperature` sama sekali, byte-identical).
- `GeminiProvider` sudah "adapter tipis" di atas `GeminiClient` (bukan
  ditulis ulang) — jalur respons (`response.text`, error mapping ke
  `ProviderResponseError`/`ProviderRateLimitError`) sudah teruji lewat
  chat utama setiap hari.
- Hasil akhirnya jauh lebih bersih untuk dirawat ke depan: SATU jalur kode
  (`provider.generate()`) untuk kedua provider, bukan dua jalur berbeda.

Saya dokumentasikan pertimbangan ini secara terbuka (bukan diam-diam)
supaya GPT/Teacher bisa menilai apakah trade-off ini sesuai preferensi,
mengingat jalur Gemini extraction lama memang sudah "terbukti jalan".

### 3. Default `MEMORY_PROVIDER=gemini`, BUKAN ikut default `AI_PROVIDER=local`

Spec §27 eksplisit: "Language Provider = Local" TIDAK otomatis berarti
"Memory Provider = Local" — dua keputusan terpisah. Saya pertahankan
`MEMORY_PROVIDER` default ke **"gemini"**, dengan alasan yang sama persis
seperti kenapa `AI_PROVIDER` baru dipindah ke "local" di v2.0 Step 9:
**setelah** Full Regression selesai dan **dikonfirmasi Teacher lewat
testing nyata** — bukan cuma karena gratis/lokal. Siklus konfirmasi yang
sama belum terjadi untuk kualitas ekstraksi Local (dan tidak bisa terjadi
di sandbox saya — lihat bagian "Keterbatasan" di bawah). Sampai itu
terjadi, default aman = provider yang sudah v2.1-verified.

### 4. Tidak ada `LOCAL_MEMORY_MODEL_NAME`/`LOCAL_MEMORY_BASE_URL` baru

Spec §20 eksplisit: implementasi pertama **tidak** boleh membuat server LM
Studio kedua secara otomatis. Local Memory Extraction (kalau diaktifkan)
bicara ke **server & model LM Studio yang sama** dengan chat utama
(`LOCAL_PROVIDER_MODEL_NAME`/`LOCAL_PROVIDER_BASE_URL`, reuse penuh, nol
config baru). Ini juga konsekuensi alami dari §18: TIDAK menambah worker
count/thread pool sekadar karena Local inference lebih lambat — satu model
LM Studio, satu request pada satu waktu (baik dari chat maupun dari
Memory worker v2.1 yang sudah serial).

### 5. Category whitelist — sudah ada, tidak dibuat ulang

Spec §36 minta validasi "supported category?" tapi eksplisit melarang bikin
sistem validasi skema besar. Saya cek: `database/memory_manager.py` sudah
punya `VALID_CATEGORIES = {"preference", "relationship", "identity",
"project", "schedule", "general"}` dan `save_memory()` sudah otomatis
fallback kategori tak dikenal ke `"general"` (bukan menolak/crash). Ini
**sudah cukup** untuk kebutuhan §36 (lapisan pertahanan terakhir sebelum
tulis DB sudah ada) — saya tidak menduplikasi whitelist ini di
`MemoryExtractor` supaya tidak ada dua sumber kebenaran yang bisa
berbeda dari waktu ke waktu.

## Larangan yang Dipatuhi (Spec §"Guardrail")

Tidak ada satupun berikut yang dibuat: Memory System v2, Vector DB, RAG,
Memory Agent, `MemoryManager` kedua, `MemoryExtractor` yang dipaksa cocok
dengan `LanguageModelProvider` tanpa verifikasi (justru sebaliknya —
diverifikasi dulu, baru diputuskan cocok), migrasi Vision/TTS, Plugin
System, Outfit System. Async dari v2.1 **tidak hilang** — `MemoryExtractor`
tetap authority ekstraksi, `MemoryManager` tetap satu-satunya authority
persistence, autonomous interaction (`check_autonomous_opportunity()`)
tetap **tidak** menjadwalkan memory extraction, persis keputusan v2.1
(tidak disentuh sama sekali di v2.2).

## Verifikasi yang Sudah Dilakukan (Sandbox, Offline)

Sandbox saya **tidak punya akses jaringan** (tidak bisa `pip install`
`google-genai`/`loguru` asli, tidak bisa menghubungi LM Studio/Gemini
sungguhan). Saya buat stub minimal (`google.genai`, `loguru`) khusus untuk
testing offline — **stub ini TIDAK termasuk dalam file yang diserahkan**,
murni alat bantu verifikasi lokal saya.

✅ **Full compile sweep** — seluruh `.py` di project (bukan cuma yang
diubah) lolos `py_compile`, nol regresi sintaksis.

✅ **`MemoryExtractor` — 8 skenario, provider palsu (`FakeProvider`)**:
1. JSON valid bersih → fakta tersimpan sesuai.
2. Array kosong (small talk) → `[]`, tidak ada fakta dipaksakan.
3. **JSON dibungkus code fence** (simulasi model Local yang kurang patuh
   instruksi "balas HANYA JSON") → **aman diabaikan, TIDAK di-parse paksa,
   TIDAK crash, TIDAK menghasilkan fakta palsu**.
4. JSON valid tapi bukan array (dict tunggal) → aman diabaikan.
5. Array campuran item valid+tidak valid → **cuma item valid yang
   disimpan**, item rusak diabaikan diam-diam (bukan menggagalkan semua).
6. `ProviderError` (simulasi LM Studio down/network gagal) → `[]`,
   tidak crash, tertangkap terpisah dari exception umum.
7. Exception tak terduga apa pun → tetap `[]` (jaring pengaman terakhir).
8. String kosong dari provider → `[]`.

✅ **`GeminiClient`/`GeminiProvider` — backward compatibility**:
- Tanpa `temperature` (jalur chat utama, tidak berubah) → object config
  **tidak punya field `temperature` sama sekali** — dikonfirmasi lewat
  `hasattr()`, bukan cuma asumsi.
- Dengan `temperature=0.0` (jalur extraction baru) → tersimpan benar di
  config, diteruskan benar dari `GeminiProvider` ke `GeminiClient`.

✅ **`LocalProvider` — konstruksi untuk Memory Extraction** — dikonfirmasi
bisa dikonstruksi dengan `system_prompt=EXTRACTION_SYSTEM_PROMPT`,
`temperature=0.0`, dst, **tanpa perubahan apa pun** ke `local_provider.py`
itu sendiri (semua parameter sudah ada sejak v2.0).

## Belum/Tidak Dilakukan di Sesi Ini (Keterbatasan Sandbox)

Sama seperti v2.1, sandbox saya tidak punya akses jaringan sama sekali.
Yang **tidak bisa** saya lakukan dari sini:

- ❌ **Test kualitas ekstraksi Local sungguhan** — ini yang PALING penting
  dan tidak bisa saya gantikan. Spec §38 minta test eksplisit untuk
  kategori: *explicit fact*, *noise*, *ambiguity*, *contradiction*,
  *unsupported inference* — semua ini butuh model Local (`qwen3-vl-8b`
  atau apa pun yang Teacher pakai) **sungguhan** merespons prompt
  `EXTRACTION_SYSTEM_PROMPT`, bukan simulasi `FakeProvider` seperti test
  saya di atas. Test saya membuktikan **pipa/pagar pengaman kode** bekerja
  benar (JSON rusak tidak lolos, error tidak crash) — bukan membuktikan
  **model Local sungguhan** cukup akurat/konservatif untuk dipercaya.
- ❌ **Resource contention test** (spec eksplisit meminta ini) — chat cepat
  berturut-turut SAMBIL memory extraction Local jalan di background, di
  server LM Studio **yang sama** — perlu LM Studio hidup dan diamati
  latency chat secara langsung. Saya tidak bisa mensimulasikan beban
  inference sungguhan di sandbox ini.
- ❌ `main_gui.py`/Settings GUI belum dijalankan sungguhan (Qt real, bukan
  cuma `py_compile`).

**Rekomendasi test manual untuk Teacher** (urutan disarankan):

1. **Baseline dulu** — set `MEMORY_PROVIDER=gemini` (default, tidak perlu
   diubah), pastikan chat & memory masih bekerja normal seperti v2.1
   sebelum mencoba Local sama sekali (regression check murni ini dulu).
2. Set `MEMORY_PROVIDER=local` di `.env` (atau lewat Settings GUI baru →
   restart), pastikan `LOCAL_PROVIDER_MODEL_NAME` menunjuk model yang
   sedang di-load LM Studio.
3. Kirim pesan yang **jelas** mengandung fakta (mis. "aku suka kopi
   hitam") → buka Memory GUI setelah beberapa detik, pastikan tersimpan
   dengan kategori yang masuk akal.
4. Kirim pesan **basa-basi murni** ("halo", "wkwk") → pastikan **tidak**
   ada memori baru tersimpan (test "noise").
5. Kirim pesan **ambigu** (mis. "mungkin aku suka kopi kali ya") → amati
   apakah Local model terlalu percaya diri menyimpan ini sebagai fakta
   pasti (kalau iya, ini sinyal Local belum cukup konservatif untuk jadi
   default).
6. Kirim pesan yang **bertentangan** dengan fakta lama (mis. sebelumnya
   bilang suka kopi, sekarang bilang sudah berhenti minum kopi) → amati
   apakah tersimpan sebagai entri baru yang masuk akal, bukan kebingungan.
7. **Sambil** melakukan test di atas, perhatikan **kecepatan balasan chat
   utama** — apakah terasa lebih lambat/tersendat saat extraction Local
   sedang jalan di background (resource contention, satu server LM Studio
   dipakai dua permintaan hampir bersamaan).
8. Buka Developer Dashboard → card "Memory Extraction (Async)" sekarang
   harus menunjukkan baris "Provider: Local" paling atas.

Kalau dari hasil test ini kualitas Local dirasa cukup konsisten & konservatif
(minim false positive di kasus ambigu), Teacher/GPT bisa memutuskan pindah
default `MEMORY_PROVIDER` ke `"local"` — persis siklus yang sama seperti
`AI_PROVIDER` di v2.0 Step 9, bukan keputusan saya yang buat sepihak di sini.
