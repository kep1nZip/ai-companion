# V3.4 — Memory Relevance Ranking & Context Quality

## 0. Milestone Identity

**Version:** v3.4  
**Name:** Memory Relevance Ranking & Context Quality  
**Status:** PLANNED  
**Previous milestone:** v3.3 — Contextual Recall & Reference Intelligence  
**Primary goal:** Improve the quality and ordering of retrieved memories before they are inserted into LLM context, without introducing a second intelligence layer, vector database, embeddings, RAG, or provider-specific behavior.

---

# 1. Objective

v3.3 improved **where memory retrieval comes from**:

- current user message
- conversation anchor
- fresh vision context
- existing recency fallback

However, retrieval results can still contain multiple memories with different levels of relevance.

v3.4 therefore focuses on:

> **retrieving candidate memories, ranking them deterministically, removing duplicates, and selecting the strongest results before they reach the LLM.**

The milestone must improve context quality while preserving the existing architecture.

The desired flow becomes:

```text
Teacher message
      ↓
v3.3 contextual retrieval
      ↓
candidate memories
      ↓
v3.4 deterministic relevance ranking
      ↓
deduplication / selection
      ↓
clean memory context
      ↓
ContextBuilder / LLM
```

---

# 2. Architectural Principle

v3.4 is a **retrieval quality layer**, not a new reasoning system.

It may answer:

> "Which retrieved memories are more relevant according to deterministic application signals?"

It must NOT answer:

> "What does Teacher really mean?"

> "Which ambiguous reference is semantically correct?"

> "What should Arona say?"

Those remain downstream responsibilities.

The architecture remains:

```text
                         ┌─────────────────────┐
                         │      Teacher        │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │      Companion      │
                         │     orchestrator    │
                         └──────────┬──────────┘
                                    │
                     v3.3 contextual retrieval
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Memory Candidates   │
                         └──────────┬──────────┘
                                    │
                         v3.4 relevance ranking
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Ranked Memory Set   │
                         │ + deduplication     │
                         └──────────┬──────────┘
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │ Context / LLM       │
                         └─────────────────────┘
```

# 5. Phase 1 — Define Deterministic Relevance Signals

Create or reuse a single deterministic relevance calculation.

Possible signals:

### 5.1 Exact / Strong Keyword Match

A memory matching more meaningful query keywords should score higher.

Example:

```text
Query:
"debugging backend LeadEstate"

Memory A:
"Teacher sedang mengerjakan backend LeadEstate"

Memory B:
"Teacher suka menggunakan Java"
```

Memory A should receive a stronger relevance score.

---

### 5.2 Keyword Coverage

A candidate matching multiple significant query terms should score higher than a candidate matching only one.

Example:

```text
candidate A → debugging + backend + leadestate
candidate B → backend
```

Candidate A ranks above candidate B.

---

### 5.3 Phrase / Project Name Match

An exact project/entity match should carry strong deterministic weight.

Example:

```text
"LeadEstate"
```

matching:

```text
"backend LeadEstate"
```

is more useful than a generic substring match.

---

### 5.4 Query Source Priority

Existing v3.3 query sources may have different context meaning.

Potential source categories:

```text
current_message
conversation_anchor
vision_context
recency_fallback
```

Do NOT assume a fixed ordering until Phase 0 confirms how the existing retrieval flow works.

If source priority is introduced, it must be explicit, deterministic, and justified by the existing architecture.

---

### 5.5 Recency

Recent memories may receive a deterministic tie-break or modest relevance contribution.

Important:

Recency MUST NOT automatically overpower topical relevance.

Example:

```text
old LeadEstate memory
vs
recent unrelated Arona memory
```

The unrelated recent memory must not automatically win merely because it is newer.

---

### 5.6 Memory Status

Only active memory should normally enter the ranking set.

Superseded memory must remain governed by the existing v2.5/v2.6 semantics.

Do NOT reintroduce superseded memories simply for ranking.

---

# 6. Phase 2 — Deterministic Ranking Function

Create one centralized ranking function.

Conceptually:

```python
ranked = rank_memories(
    memories,
    query_keywords=...,
    query_source=...,
    ...
)
```

The exact API must follow the existing project architecture after Phase 0.

The function must:

1. accept existing retrieved memory candidates
2. compute deterministic relevance signals
3. produce a stable ranking
4. preserve enough metadata for observability
5. avoid database schema changes
6. avoid LLM calls

A score may conceptually combine:

```text
keyword match
+ keyword coverage
+ exact entity/phrase match
+ source relevance
+ recency / tie-break
```

Do not invent arbitrary complexity.

The weighting must be documented in code comments or a nearby project note if weights are non-obvious.

---

# 7. Phase 3 — Stable Ranking

Ranking must be deterministic.

For identical inputs:

```text
same candidates
same query
same metadata
```

the output order should be identical.

Use stable secondary ordering when scores tie.

Possible deterministic tie-breakers:

```text
stronger keyword coverage
→ exact phrase match
→ newer memory
→ existing memory order / stable ID
```

Do not rely on random ordering.

---

# 8. Phase 4 — Deduplication

Review whether identical or effectively duplicated memories can appear from multiple retrieval tiers.

Example:

```text
current_message search
+
conversation_anchor search
+
vision_context search
```

may produce the same memory.

v3.4 should prevent duplicate context injection.

The implementation must:

- reuse the existing memory identity where available
- otherwise use a conservative deterministic duplicate strategy
- keep one representative
- preserve the strongest relevance metadata
- never delete or mutate the actual stored memory

This is **context deduplication**, not memory deletion.

---

# 9. Phase 5 — Candidate Selection / Context Budget

After ranking, limit the number of memories supplied to the LLM.

The exact limit MUST be based on the existing context design discovered during Phase 0.

Do not blindly introduce a large hard-coded number.

Desired pattern:

```text
Retrieved candidates
        ↓
rank
        ↓
deduplicate
        ↓
select top N
        ↓
LLM context
```

Important:

The top-N selection must not remove all candidates merely because one weak scoring function fails.

The existing fallback behavior must remain safe.

# 11. Phase 7 — Context Quality Rules

The following principles should hold.

## 11.1 Relevant beats merely recent

A highly relevant older memory can outrank a recent weakly related memory.

---

## 11.2 Specific beats generic

Example:

```text
"Teacher sedang mengerjakan backend LeadEstate"
```

should rank above:

```text
"Teacher suka programming"
```

for a LeadEstate/backend query.

---

## 11.3 Multiple matching signals beat one accidental match

A candidate matching several meaningful terms should generally rank above one matching only a generic term.

---

## 11.4 No semantic guessing

The ranking system must never invent:

```text
"this memory is definitely what Teacher means"
```

Ranking ≠ semantic resolution.

---

## 11.5 No destructive behavior

Ranking must never:

- delete memory
- modify stored memory text
- supersede memory
- change memory status

It only determines context ordering/selection.

# 16. Performance Requirements

v3.4 should remain lightweight.

Do NOT:

- call another model
- perform network-based ranking
- add a database query per candidate

```text

→ rank in memory
→ deduplicate
→ select
```

If a helper can be reused, reuse it.

Avoid duplicate keyword extraction loops.

Avoid ranking the same candidate multiple times.


# 24. Final Milestone Intent

v3.4 should make the following transition possible:

### Before

```text
Good retrieval
      ↓
many possible memories
      ↓
LLM receives noisy context
```

### After

```text
Good retrieval
      ↓
candidate memories
      ↓
deterministic relevance ranking
      ↓
duplicate removal
      ↓
strongest relevant context
      ↓
LLM
```

The key principle:

> **v3.3 decides where to look. v3.4 decides which retrieved results deserve context priority. The LLM still decides what they mean and how Arona responds.**

This keeps the architecture simple, explainable, provider-agnostic, and compatible with the existing Arona roadmap.
