**Scope dieksekusi (sesuai keputusan Teacher):** Phase 1 (Recent Interaction) + Phase 3 (Opportunity Relevance) + Phase 5+6 (Memory/Vision-aware Initiative). Memory GUI regression sudah fixed sejak v2.6 (dikonfirmasi masih aktif).

## 1. Phase 1 — Recent Interaction Awareness ✅

**Baseline diukur dulu** (bukan tebak-tebak): enumerasi seluruh kombinasi `DEFAULT_RULES` membuktikan **11 kombinasi berbeda** bisa mencapai threshold=50 tanpa kontribusi idle sama sekali — termasuk persis skenario yang diaudit (`routine_pending+relationship+mood=50`).

**Implementasi:** `RecentInteractionPenaltyRule` baru di `initiative/initiative_rules.py`.
- Reuse `idle_seconds` yang sudah ada — **nol state baru, nol timer baru, nol cooldown kedua**.
- `threshold_seconds=900` — **angka yang sama persis** dengan `IdleRule` yang sudah ada (bukan angka baru).
- `weight=-20` — **magnitude yang sama persis** dengan `IdleRule` (+20), simetris by design.
- Didaftarkan ke `DEFAULT_RULES`.

**Terverifikasi nyata:**
```
idle_seconds=0   (baru saja chat) -> Score 30/50 -> should_start=False  [DITOLAK]
idle_seconds=1000 (16+ menit idle) -> Score 70/50 -> should_start=True   [DIIZINKAN]
```
Skenario persis yang diaudit sekarang **ditolak** — dan begitu Teacher genuinely idle lama, Initiative **tidak permanen terblokir** (kembali diizinkan otomatis).

## 2. Phase 3 — Opportunity Relevance ✅

**Masalah:** `RoutineEvent.priority` (`EventPriority`: LOWEST..CRITICAL) sudah ada sebagai data, tapi `RoutinePendingRule` selalu memberi flat +25 apa pun priority-nya.

**Ekstensi kecil yang diperlukan (dijelaskan ke Teacher, bukan diam-diam):** `DecisionRule.weight` sebelumnya statis — untuk kontribusi **monotonic** sesuai priority (persis yang diminta), saya tambah method `get_weight(ctx)` dengan default `return self.weight` (nol perubahan untuk 8 dari 9 rule di `DEFAULT_RULES`), di-override HANYA di `RoutinePendingRule`. `InitiativeEngine.compute()` diubah 1 baris: `rule.weight` → `rule.get_weight(ctx)`.

**Formula (nol angka baru diciptakan):**
```
kontribusi = weight(25.0, sudah ada) × (priority.value / EventPriority.MEDIUM.value(3, sudah ada))
```

**Terverifikasi nyata (monotonic, MEDIUM = identik perilaku lama):**
```
LOWEST   -> +8.33
LOW      -> +16.67
MEDIUM   -> +25.00  (SAMA PERSIS dengan flat +25 lama — nol regresi untuk event yang sudah default MEDIUM)
HIGH     -> +33.33
CRITICAL -> +41.67
```

## 3. Phase 5 + 6 — Memory & Vision-aware Initiative ✅

**Flow diimplementasikan PERSIS sesuai keputusan desain Teacher:**
```
Fresh Vision (application + summary)
    -> query text
    -> Companion._select_relevant_memories()  [REUSE, tidak dibuat ulang]
    -> relevant_memory_count (angka, BUKAN daftar Memory)
    -> DecisionContext.relevant_memory_count
    -> MemoryRelevanceRule (bonus +10 kalau count >= 1)
```

**Batasan yang dijaga ketat (sesuai instruksi eksplisit):**
- ✅ Cuma **angka** (`relevant_memory_count`) yang masuk ke `DecisionContext` — **tidak ada** isi Memory penuh yang pernah sampai ke Initiative.
- ✅ **Nol panggilan LLM/provider** di jalur ini — `_select_relevant_memories()` murni SQL keyword search yang sudah ada sejak v1.x, sama seperti dipakai chat context.
- ✅ Initiative **tidak jadi orchestrator kedua** — Companion yang menghitung count SEBELUM memanggil `Initiative.update()`, Initiative cuma menerima angka jadi.
- ✅ Filter marker internal (v2.6) **otomatis ikut berlaku** — reuse method yang sama berarti proteksi yang sama.

**Weight `MemoryRelevanceRule = 10.0`** — dipilih dari magnitude PALING KECIL yang sudah dipakai rule lain (`MoodBonusRule`/`CuriosityRule` sama-sama 10.0), bukan angka baru — konservatif karena ini sinyal yang belum tervalidasi lewat pemakaian nyata (beda dari Phase 1 yang punya justifikasi simetris eksplisit).

**Terverifikasi nyata:**
```
Vision summary "Teacher sedang membuka aplikasi Valorant..." 
  + Memory "Teacher suka main Valorant" tersimpan
  -> relevant_memory_count=2, MemoryRelevanceRule aktif (+10)

Vision None (OFF/stale)              -> count=0, rule tidak aktif
Vision ada tapi summary/application kosong -> count=0, rule tidak aktif
Marker internal (__ARONA_...)        -> tetap terfilter (reuse proteksi v2.6)
```

6. **Full pipeline smoke test**: `behavior_state → vision → routine → initiative` dijalankan end-to-end tanpa network call, tidak crash.
