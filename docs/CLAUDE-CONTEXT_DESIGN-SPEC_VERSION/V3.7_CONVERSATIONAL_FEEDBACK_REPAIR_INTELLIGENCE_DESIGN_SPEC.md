# V3.7 — Conversational Feedback & Repair Intelligence

## 0. Milestone Identity

**Version:** v3.7  
**Name:** Conversational Feedback & Repair Intelligence  
**Status:** PLANNED  
**Previous milestone:** v3.6 — Adaptive Response Calibration & Conversational Pacing  
**Primary goal:** Make Arona respond more naturally to Teacher's feedback about the previous turn — confusion, correction, dissatisfaction, requests to simplify/repeat, acknowledgement, or closure — without introducing a second reasoning system, self-evaluation LLM, or persistent dialogue-state database.

---

# 1. Why V3.7

V3.6 already provides **per-message response calibration**.

It can expose evidence such as:

```text
Form: question
Explicit pacing: concise
Step-by-step: true
```

That improves the current response.

The next gap is:

> **What happens after Arona responds and Teacher reacts to that response?**

Examples:

```text
Teacher:
"Jelasin refresh token dong."

Arona:
[explanation]

Teacher:
"Masih bingung."

Desired behavior:
→ recognize that the previous explanation did not fully land
→ adapt the next response naturally
→ explain more simply / differently
```

Another:

```text
Teacher:
"Bukan itu maksudku."

Desired behavior:
→ recognize correction
→ do not continue defending the previous interpretation
→ repair the misunderstanding
```

Another:

```text
Teacher:
"Kepanjangan."

Desired behavior:
→ recognize explicit negative feedback about response length
→ next response should adapt toward concise
```

Another:

```text
Teacher:
"Oke ngerti, makasih."

Desired behavior:
→ recognize acknowledgement/closure
→ do not unnecessarily restart the explanation
```

V3.7 therefore introduces a **feedback/repair evidence layer**.

It does not judge Arona's own quality.

It only reports what Teacher explicitly communicates about the interaction.

---

# 2. Core Principle

The architecture may detect:

```text
Teacher is confused.
Teacher says the previous explanation was too long.
Teacher says the previous answer was wrong.
Teacher asks to repeat.
Teacher asks for a simpler explanation.
Teacher confirms understanding.
Teacher closes the topic.
```

The architecture must NOT claim:

```text
Arona's previous response was objectively bad.
Arona misunderstood Teacher.
Teacher is definitely confused.
The previous answer was incorrect.
```

unless those are directly stated by Teacher.

The application supplies **feedback evidence**.

The existing LLM interprets the evidence and generates the repair/continuation.

# 4. Hard Boundaries

## 4.1 No Self-Evaluation LLM

Do NOT introduce:

```text
response critic LLM
quality judge LLM
grader LLM
self-reflection LLM
```

Arona must not call another model to decide whether her previous answer was good.

---

## 4.2 No Hidden "Arona Was Wrong" State

Do NOT create:

```text
previous_response_quality
previous_response_correctness
misunderstanding_score
assistant_error_score
```

unless a future milestone explicitly designs such a system.

V3.7 works from Teacher's explicit feedback.

---

## 4.3 No Persistent Dialogue-State Database

Do NOT create:

```text
dialogue_state.db
conversation_feedback.db
repair_history.db
```

The existing `Conversation` history remains the source of recent conversational context.

---

## 4.4 No Second Conversation History

Do NOT maintain:

```text
feedback_history
repair_history
assistant_history
```

outside the existing Conversation mechanism.

---

## 4.5 No Response Template Engine

Do NOT create rigid branches such as:

```text
if confused:
    always apologize
    always explain with analogy
```

Feedback evidence should influence the existing LLM naturally.

---

## 4.6 No Provider-Specific Logic

Local and Gemini must receive the same application-generated feedback evidence.

No new:

```python
if provider == "local":
```

or equivalent provider-specific repair rules.

---

## 4.7 No New Personality System

Do not rewrite:

```text
prompts/system_rules.txt
prompts/personality.txt
prompts/speaking_style.txt
```

just to create "repair behavior".

---

## 4.8 No Task System

Feedback about a task does not create a task subsystem.

For example:

```text
"masih bingung dengan backend LeadEstate"
```

must remain conversational evidence, not:

```text
task_state = BLOCKED
```

# 7. Phase 2 — Explicit Feedback Beats Inference

Explicit Teacher feedback is stronger than inferred interpretation.

Example:

```text
Teacher:
"Masih bingung, jelasin lebih sederhana."
```

Evidence:

```text
feedback:
confusion

repair request:
simplification

explicit phrase:
"jelasin lebih sederhana"
```

Do not reduce this into a single abstract category such as:

```text
feedback_mode = confused
```

when multiple explicit signals exist.

Preserve the useful evidence.

Example:


Possible evidence:

```text

repeat_request
```

Do NOT force a single winner unless there is a clear existing architectural need.

# 9. Phase 4 — Correction / Misunderstanding Repair

A correction cue is especially important.

Example:

```text
Teacher:
"Bukan itu maksudku."
```

Application-level evidence:

```text
correction detected
```

Application MUST NOT generate:

```text
Arona misunderstood Teacher.
```

Instead, context may say:

```text
Teacher explicitly indicates that the previous interpretation was not what they meant.
```

The LLM then decides how to repair naturally.

---

# 10. Phase 5 — Response-Length Feedback

V3.6 handles explicit current-message pacing cues.

V3.7 adds **feedback about the previous response**.

Example:

```text
Teacher:
"Kepanjangan."
```

This should be distinguishable from:

```text
"Langsung aja, jangan panjang."
```

because the first is feedback about the preceding response, while the second is an instruction about the next response.

Both may produce concise-oriented evidence, but their source should remain truthful.

Suggested evidence:

```text
source = previous_response_feedback
```

versus:

```text
source = current_message_instruction
```

# 12. Phase 7 — Repeat / Re-explain Requests

Examples:

```text
"jelasin lagi"
"ulang dari awal"
"coba jelasin lagi"
```

These are not necessarily new topics.

They are feedback about the previous turn.

The application should preserve this distinction.

Possible evidence:

```text
repeat_request = true
reference_to_previous_response = true
```

Do not accidentally trigger memory retrieval as if the user introduced a new topic.

Existing reference logic may still operate if the wording also contains a valid contextual reference.

---

# 13. Phase 8 — Positive Feedback and Closure

Positive feedback matters because Arona should know when NOT to keep explaining.

Examples:

```text
"Oke ngerti."
"Sip, paham."
"Udah ngerti, makasih."
```

Possible evidence:

```text
positive_acknowledgement
closure
```

The application must NOT force:

```text
conversation_should_end = true
```

It simply supplies evidence.

The LLM can naturally acknowledge or continue when appropriate.
