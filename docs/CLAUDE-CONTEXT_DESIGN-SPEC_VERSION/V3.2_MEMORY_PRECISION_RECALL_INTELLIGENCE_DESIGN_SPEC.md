# V3.2 — Memory Precision & Recall Intelligence

## Status

**Planned**

V3.2 melanjutkan fondasi memory dari v2.5, context intelligence dari v2.6-v2.9, personalization v3.0, dan adaptive presence v3.1.

Fokus utama:

> Arona bukan hanya mampu menyimpan memory, tetapi semakin tepat menentukan apa yang layak dipertahankan dan apa yang layak dipanggil kembali.

Prinsip utama:

```text
Reuse existing systems > create new systems
Measure before optimize
Smallest safe change
```

---

# 1. Tujuan Utama

Fondasi memory yang sudah ada:

```text
Memory Extraction
      ↓
MemoryManager
      ↓
Relevance
      ↓
Supersession
      ↓
Context
      ↓
Companion
```

V3.2 tidak membuat arsitektur memory baru.

Targetnya adalah meningkatkan dua hal:

```text
PRECISION
→ memory yang tersimpan memang layak diingat

RECALL
→ memory yang relevan benar-benar ditemukan saat dibutuhkan
```

Contoh:

```text
Teacher:
"Aku suka game X."

→ stable preference
→ layak disimpan

Teacher:
"Lagi pengen belajar Rust malam ini."

→ temporary/current intent
→ tidak otomatis dianggap stable preference
→ bisa menjadi project/general context bila aturan existing memang menganggapnya layak
```

Dan ketika memory relevan dibutuhkan:

```text
Teacher:
"lanjut yang kemarin"

→ existing relevance/context machinery mencari memory yang benar
→ bukan random recent memory
```

---

# 2. Hard Boundaries

V3.2 **tidak** boleh mengubah batas arsitektur menjadi:

```text
❌ Conversation persistence database
❌ Vector database
❌ RAG pipeline
❌ Multi-agent
❌ Second LLM
❌ MemoryManager2
❌ New memory database
❌ New autonomous planner
❌ Plugin System
❌ Outfit System
```

Tetap:

```text
Conversation
→ short-term / process-lifetime conversation

Memory
→ persistent facts/context yang memang layak dipertahankan
```

Jangan mengubah semua percakapan menjadi memory.

# 3. Phase 0 — Memory Architecture Audit

## Wajib dilakukan sebelum kode berubah

Claude harus inspect repository aktual terlebih dahulu.

Audit minimal:

```text
ai/memory_extractor.py
database/memory_manager.py
ai/context_builder.py
ai/companion.py
initiative/*
developer/*
relevant prompt files
existing tests
```

Cari dan dokumentasikan:

1. Bagaimana candidate memory dibuat.
2. Bagaimana stable preference dikenali.
3. Bagaimana temporary/current activity dikenali.
4. Bagaimana kategori `preference`, `project`, `general`, dan kategori lain yang benar-benar sudah ada dipakai.
5. Bagaimana confidence saat extraction bekerja.
6. Bagaimana duplicate/update/supersession bekerja.
7. Bagaimana `_select_relevant_memories()` bekerja.
8. Apakah query recall sudah normalisasi atau hanya exact/semantic matching.
9. Apakah ada bias recency yang masih relevan.
10. Apakah sebagian besar target v3.2 ternyata sudah tersedia.

### Aturan audit

Jangan mengubah kode selama Phase 0.

Jika sebuah phase ternyata sudah substansial ada:

```text
→ tandai sebagai ALREADY SATISFIED
→ regression test
→ jangan rewrite
```

# 4. Phase 1 — Project / Activity Memory Quality

## Tujuan

Meningkatkan kemampuan extraction membedakan:

```text
STABLE FACT
STABLE PREFERENCE
CURRENT PROJECT
CURRENT ACTIVITY
TEMPORARY INTENT
CASUAL CHAT / NOISE
```

Contoh:

```text
"Aku suka React."
→ preference

"Aku sedang mengerjakan LeadEstate."
→ project

"Aku lagi debugging login."
→ current project/activity context

"Aku lagi pengen belajar Rust."
→ temporary intent / general/project tergantung konteks

"wkwk capek"
→ jangan dipaksa menjadi memory
```

## Constraint

Gunakan `EXTRACTION_SYSTEM_PROMPT` dan logic extraction yang sudah ada sebelum mempertimbangkan code/schema change.

Prioritas:

```text
prompt refinement
>
small extraction logic refinement
>
schema change (hanya jika evidence benar-benar menuntut)
```

Jangan membuat kategori baru hanya karena satu contoh.

---

# 5. Phase 2 — Stable Preference Detection Refinement

V3.0 sudah memiliki guidance untuk stable preference vs temporary intent.

Phase ini hanya boleh menambah perubahan bila audit menemukan failure case nyata.

## Target

Lebih konsisten membedakan:

```text
Stable:
"Aku suka game X."
"Aku biasanya pakai VS Code."

Temporary:
"Lagi pengen coba editor Y."
"Kayaknya malam ini mau main game Z."
```

## Hard rule

Jangan menggunakan satu keyword secara naif sebagai penentu absolut.

Contoh:

```text
"Lagi selalu pakai VS Code."
```

tidak boleh otomatis diklasifikasikan hanya berdasarkan kata `lagi`.

Gunakan keseluruhan konteks kalimat.

---

# 6. Phase 3 — Memory Confidence & Specificity

## Tujuan

Memory yang masuk harus memiliki informasi yang cukup spesifik untuk berguna kembali.

Audit terlebih dahulu apakah confidence dan validation sebenarnya sudah tersedia.

Contoh memory yang lebih baik:

```text
"Teacher uses VS Code for programming."
```

daripada:

```text
"Teacher likes coding."
```

jika statement source memang mendukung specificity tersebut.

## Prinsip

Jangan memperkaya atau menebak fakta.

```text
Source says X
→ store X

Source does not say Y
→ do not infer Y
```

Confidence digunakan untuk membantu extraction/selection bila mechanism existing memang mendukungnya.

Jangan membuat threshold angka baru tanpa evidence.

---

# 7. Phase 4 — Recall Quality

## Tujuan

Memory yang tepat harus muncul saat context membutuhkannya.

Existing machinery yang harus diprioritaskan:

```text
_select_relevant_memories()
```

Jangan membuat recall engine kedua.

Target:

```text
Query:
"lanjut project backend yang kemarin"

Relevant:
→ backend/project memory

Irrelevant:
→ random recent memory
→ casual chat
→ unrelated preference
```

## Recall test categories

Minimal validasi:

```text
1. Exact topic
2. Synonym / natural phrasing
3. Project reference
4. Preference reference
5. Multiple relevant memories
6. Irrelevant memory filtering
7. Superseded memory filtering
```

Recall harus tetap menghormati active/superseded semantics dari v2.5-v2.6.

---

# 8. Phase 5 — Memory Conflict / Supersession Refinement

## Tujuan

Memastikan memory yang berubah tidak menyebabkan recall kontradiktif.

Existing semantics:

```text
NEW
DUPLICATE
UPDATE
SUPERSEDES
```

Pertahankan model ini.

Contoh:

```text
"Aku suka game X."
       ↓
"Aku sekarang lebih sering main game Y."
```

Memory lama tidak boleh digunakan seolah-olah tetap menjadi preference aktif bila sistem menentukan bahwa memory baru memang supersedes/update memory lama.

## Constraint

Jangan redesign supersession jika implementation v2.5 sudah benar.

Phase ini terutama:

```text
audit
→ edge-case test
→ smallest safe fix only
```

---

# 9. Phase 6 — Memory Explainability

## Tujuan

Teacher/Developer dapat memahami secara sederhana mengapa sebuah memory:

```text
saved
not saved
updated
superseded
recalled
not recalled
```

## Bentuk yang diutamakan

Gunakan observability yang sudah ada.

Contoh:

```text
Memory Decision:
UPDATE

Reason:
New statement conflicts with active preference.

Recall:
Relevant

Relevance Signal:
Project match
```

Jangan expose chain-of-thought.

Explainability hanya boleh menampilkan deterministic metadata/signal yang memang tersedia.

# 13. Definition of Done

V3.2 hanya boleh dinyatakan **PASS** apabila:

1. Phase 0 audit selesai.
2. Stable preference vs temporary intent lebih konsisten.
3. Project/activity context ditangkap sesuai evidence dan rules.
4. Memory tidak menyimpan noise hanya demi menambah jumlah memory.
5. Recall lebih tepat dan tidak mengandalkan random recent memory.
6. Active/superseded memory semantics tetap benar.
7. Existing supersession architecture tidak rusak.
8. Explainability hanya menampilkan metadata/signal yang benar-benar tersedia.
9. Developer observability tidak mengklaim hasil yang tidak bisa dibuktikan.
10. Tidak ada Conversation DB baru.
11. Tidak ada vector DB/RAG.
12. Tidak ada second LLM.
13. Tidak ada MemoryManager2.
14. Existing v1.0-v3.1 behavior tetap aman.
15. Teacher menjalankan `main_gui.py`.
16. Teacher memvalidasi extraction + recall + supersession secara nyata.
17. Tidak ada klaim PASS berdasarkan simulasi semata.

# 15. Architecture Boundaries

Pertahankan ownership:

```text
Companion
→ single orchestrator

MemoryExtractor
→ extraction only

MemoryManager
→ persistent memory storage/lifecycle

ContextBuilder
→ context assembly only
→ not LLM caller
→ not memory owner

Conversation
→ immediate conversation history

Initiative
→ speak / don't speak decision

Relationship
→ relationship state

Emotion
→ emotion state

Developer Dashboard
→ read-only observability
```

Do not move memory ownership into Companion, ContextBuilder, or Developer UI.

# 20. Success Definition

V3.2 berhasil ketika:

```text
Teacher says something
        ↓
System evaluates whether it is worth remembering
        ↓
Memory is stored only when justified
        ↓
Memory remains correct when facts change
        ↓
Teacher later references a topic
        ↓
Relevant memory is recalled
        ↓
Irrelevant / superseded memories stay out
```

Target akhir:

> Arona memiliki memory yang lebih kecil kemungkinan salah simpan, lebih kecil kemungkinan lupa informasi yang relevan, dan lebih kecil kemungkinan mengingat hal yang seharusnya sudah tidak aktif — tanpa membuat arsitektur memory menjadi kompleks.
