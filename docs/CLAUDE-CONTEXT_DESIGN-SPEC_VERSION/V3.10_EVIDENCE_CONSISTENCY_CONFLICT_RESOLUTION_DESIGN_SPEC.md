# V3.10 — Evidence Consistency & Conflict Resolution

## 0. Milestone Identity

**Version:** v3.10  
**Name:** Evidence Consistency & Conflict Resolution  
**Status:** PLANNED — audit first, implementation only when a reproducible gap is found  
**Previous milestone:** v3.9 — Adaptive Context Budget & Attention Allocation  
**Primary goal:** Ensure Arona uses the correct scope and precedence when existing context sources appear to disagree, without adding a second reasoning system, changing memory semantics casually, or imposing a blanket “newest evidence always wins” rule.

> **Core principle:** Resolve conflicts by evidence type, scope, and explicit user intent—not by blindly trusting whichever signal is newest, longest, or easiest to retrieve.

---

# 1. Why V3.10

The existing conversation/context stack already has separate capabilities:

```text
v3.2  Memory Quality
v3.3  Contextual Recall & Reference Intelligence
v3.4  Memory Relevance Ranking & Context Quality
v3.5  Temporal Awareness & Task Continuity
v3.6  Adaptive Response Calibration & Conversational Pacing
v3.7  Conversational Feedback & Repair Intelligence
v3.8  Context-Aware Initiative & Proactive Support
v3.9  Context measurement and honest per-section observability
```

These capabilities can all be working correctly in isolation while an edge case remains possible: two valid pieces of evidence may point in different directions, or one signal may be interpreted outside the scope for which it was intended.

Examples of **potential conflicts to audit, not assumed bugs**:

- Arona knows the user usually prefers concise answers, but the current message explicitly asks for a detailed explanation.
- A retrieved older memory mentions a previous project stack, while the current message explicitly corrects that stack.
- The conversation moved from Topic A to Topic B, and the user explicitly asks to return to Topic A. “Newest topic wins” would be wrong.
- A temporal signal is inferred from a vague phrase, while the user also states an explicit date or time.
- A message contains genuinely conflicting instructions, and the system should not silently pretend the intent is unambiguous.
- Conversation feedback requests a shorter answer, while an unrelated stable preference or older calibration cue suggests a different style.

V3.10 is **not** permission to rewrite every context module. Phase 0 must find out whether current code already handles these cases correctly. Existing prompt/history behavior may already be enough.

## 1.1 Required Outcome

At the end of v3.10, we must be able to state—using inspected code and reproducible tests—one of the following:

1. **ALREADY SATISFIED:** existing behavior resolves the tested conflicts correctly; preserve the code and document the evidence.
2. **IMPLEMENTED:** a specific reproducible conflict bug was found and a small deterministic fix was necessary.
3. **CONDITIONAL PASS:** one low-risk gap is fixed, but a clearly documented scenario still needs Teacher’s manual verification.

Do not introduce a new subsystem merely to make this milestone look larger.

# 2. Scope and Non-Goals

## 2.1 In Scope

- Audit precedence among the existing current message, recent conversation, explicit reference/correction signals, memory recall, temporal evidence, response calibration, and conversational feedback.
- Define **scope-aware** precedence only where a reproducible gap exists.
- Preserve explicit topic returns and references to older conversation turns.
- Separate a one-turn instruction from a durable preference or memory update.
- Prevent an inferred signal from silently overriding a more explicit, relevant statement.
- Ask a focused clarification question when a conflict is genuinely unresolved, rather than fabricating certainty.
- Extend existing read-only Developer Dashboard observability only if it materially helps diagnose a reproduced issue and the current UI can support it safely.
- Verify Local and Gemini use the same application-side precedence logic.

## 2.2 Out of Scope

V3.10 must NOT:

- Add another LLM, classifier, agent, planner, or decision engine.
- Add embeddings, vector databases, RAG frameworks, or semantic search infrastructure.
- Add a new memory database, conversation database, user-profile database, or task database.
- Change the memory schema or introduce new permanent memory semantics without a separate explicit design.
- Automatically write a memory just because a user gives a one-turn instruction or corrects the current answer.
- Rewrite v3.3 reference resolution, v3.4 ranking, v3.5 temporal parsing, v3.6 calibration, or v3.7 feedback detection wholesale.
- Activate a conversation-history cap or change the v3.9 decision to keep `CONVERSATION_HISTORY_MAX_MESSAGES` unbounded by default.
- Add arbitrary numeric confidence scores, fabricated “evidence strength” metrics, or a universal fixed ordering that ignores scope.
- Merge Initiative with Routine or generation. Initiative remains decision-only: YES/NO about proactive speech, never language generation.
- Change `_build_autonomous_contents()` or autonomous prompt construction unless Phase 0 proves a direct, in-scope defect; normal chat and autonomous flows remain separate.
- Change Vision provider selection, freshness rules, VoiceManager, AvatarManager, GUI presentation architecture, or introduce an Outfit/Plugin System.

Rules:

- `Companion` remains the single orchestrator.
- `ContextBuilder` remains assembly/formatting-focused; do not turn it into a memory owner, LLM caller, or general reasoning engine.
- Existing evidence modules should continue to report signals, not generate natural-language replies.
- Evidence precedence must be deterministic and provider-independent if code changes are required.
- No new module is mandatory. Add one only if the audit proves that a small dedicated helper makes ownership clearer than modifying an existing narrow boundary.
- Keep current normal-chat flow and the autonomous flow separate.
- No changes to the data model or persistent user data should be required for this milestone.

# 4. Key Design Rule: Precedence Is Scope-Aware

**Do not implement a simplistic rule such as “the newest evidence always wins.”** It would break valid references to an older topic, stable preferences, and requests to continue previous work.

Use the following as an audit/design matrix. It is a behavioral contract for tested cases, not an instruction to build a large priority engine.

| Evidence conflict | Expected handling | Scope |
|---|---|---|
| Stable preference says “usually concise”; current message says “explain in detail” | Follow the explicit current instruction | Current turn only, unless the user explicitly says the preference changed permanently |
| Current message directly corrects Arona’s interpretation | Prefer the correction over the interpretation being corrected | Current issue/topic; do not automatically persist it as a global memory |
| Current message explicitly returns to an older topic (“balik ke API yang tadi”) | Resolve the referenced older topic instead of blindly following the most recent topic | Referenced topic |
| Relevant older memory and explicit current statement disagree | Do not silently let the older memory override the explicit current statement in the current response | Current turn/topic; persistent memory update remains the responsibility of existing memory logic |
| Stable preference has no explicit current-turn override | Use the stable preference if it is relevant and already supported by existing retrieval | General default within its existing scope |
| Inferred temporal cue conflicts with an explicit date/time supplied by the user | Preserve the explicit date/time; do not silently replace it with an inference | Current request |
| Vague temporal phrase such as “nanti” or “minggu depan” has no unambiguous normalization | Keep it as a raw cue or treat it as unresolved, following v3.5 behavior | Current request |
| Two instructions in the same message genuinely conflict with no clear correction order | Ask one short clarification question; do not invent a priority or confidence score | Current request |
| A one-turn style request (“kali ini singkat aja”) conflicts with the user’s usual style | Follow the one-turn request without rewriting a durable preference | Current turn only |
| Feedback indicates “masih bingung, jelasin lebih gampang” | Preserve the v3.7 repair intent; do not let unrelated older calibration erase it | Current repair turn |

## 4.1 Explicit Correction vs. Inferred Interpretation

A correction such as “bukan itu maksudku” or “bukan yang itu” should update how Arona interprets the current exchange. It must not automatically become a permanent memory unless existing memory extraction independently classifies an explicit durable fact and its established logic supports that operation.

Do not add correction-specific memory writes as a shortcut.

## 4.2 Current Instruction vs. Durable Preference

A local request does not imply a global preference change:

```text
Known default: user usually likes concise answers.
Current request: “Untuk bagian ini, jelasin detail dan kasih contoh.”
Expected: give a detailed answer for this request.
Not expected: permanently rewrite the stored preference to “likes detailed answers.”
```

A global change should only be inferred when the user explicitly communicates that it is durable, and then only through existing memory rules.

## 4.3 Older Reference vs. Newer Topic

The latest topic is not automatically the intended topic. Preserve v3.3 reference behavior for requests such as:

```text
Topic A → Topic B → Topic C → “balik ke Topic A tadi”
```

The current message’s reference determines the target. Do not drop required history or change reference retrieval merely to simplify precedence.

## 4.4 Genuine Ambiguity

Do not call two signals contradictory merely because they concern different scopes. For example, “I usually want short answers” and “explain this one in detail” are compatible: one is a default, the other is a current override.

When the actual instruction is internally contradictory and there is no clear self-correction (for example, “jawab hanya satu kata tapi jelaskan semua langkahnya”), a concise clarification is safer than silently choosing one side.

If an explicit self-correction is clear (“jelaskan detail—eh, cukup ringkas saja”), follow the final corrected intent for this turn. This must be tested without making a brittle rule that every final clause always wins.

# 7. Phase 2 — Minimal Deterministic Resolution (ONLY IF AUDIT JUSTIFIES IT)

Implement the smallest fix that resolves a demonstrated issue.

Possible acceptable changes, depending on findings:

- Correct an existing prompt/context section so explicit current-turn instructions are not undermined by older default preferences.
- Preserve a current explicit correction/reference in the shared application-side context.
- Fix a signal scope/formatting bug where a one-turn instruction is mistakenly represented as a durable preference, or vice versa.
- Add one narrow deterministic helper only if current ownership boundaries cannot safely express the required precedence.
- Add a targeted regression test for the reproduced case.

These are examples, **not a requirement to change all of them**.

Implementation constraints:

1. No new LLM calls and no provider-specific arbitration.
2. No arbitrary priority numbers or numeric confidence values.
3. No permanent memory write caused solely by a one-turn correction or style request.
4. No database schema migration.
5. No destructive mutation of conversation history.
6. No blanket removal of conflicting evidence before checking whether the evidence has different scopes.
7. Preserve reference resolution to older topics.
8. Preserve v3.5’s conservative treatment of ambiguous time phrases.
9. Reuse existing formatter/empty-section behavior from v3.9; do not reintroduce context measurement drift.
10. Do not change production behavior for a merely hypothetical concern.

If multiple fixes seem possible, prefer the one with the smallest change surface and best regression coverage. Explain why it is sufficient.

# 12. PASS / CONDITIONAL PASS / FAIL Criteria

## PASS — ALREADY SATISFIED

- Phase 0 identifies no reproducible conflict-handling defect, or every required behavior is already covered and works.
- No unnecessary production code change is made.
- Existing relevant test coverage is referenced, with only targeted tests added if valuable.
- Regression suites and compile checks pass.
- The execution report clearly explains why “no code change” is the correct outcome.

## PASS — IMPLEMENTED

- At least one concrete conflict bug is reproducible before the change.
- The fix is narrow, deterministic, scope-aware, and provider-independent.
- No new database, LLM, agent, or memory system is introduced.
- Relevant v3.3–v3.9 regressions and compile checks pass.
- Manual verification steps are prepared for Teacher.

## CONDITIONAL PASS

- A low-risk, in-scope fix and automated tests pass, but a specific runtime behavior still requires Teacher’s verification; or a non-critical edge case remains with an explicit reason and mitigation.

## FAIL

- Current explicit user instructions can still be silently overridden by stale/default evidence in a reproduced case.
- Topic return/reference behavior regresses.
- One-turn directions unexpectedly mutate durable memory/preferences.
- Application-side behavior differs by provider without an existing architectural reason.
- Changes introduce unapproved architecture, persistent state, or unrelated GUI/voice/avatar behavior.
- Tests are skipped/rewritten without a justified explanation, or manual runtime verification is falsely claimed as complete.

# 15. Final Principle

V3.10 is not intended to make Arona more complicated. It is intended to make her **consistent about which evidence applies to which situation**.

A current instruction can override a default without rewriting a stable preference. A correction can repair the current interpretation without becoming a permanent memory. An explicit reference can return to an older topic without being defeated by recency. And when the user's intent is genuinely unclear, Arona should not pretend otherwise.

**Inspect first. Prove the conflict. Make the smallest safe change—or preserve the existing implementation when it is already correct.**
