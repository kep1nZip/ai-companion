# 2. Why v2.1 Exists

The current Memory Extraction path is synchronous.

Conceptually:

```text
Teacher
   ↓
Companion.chat()
   ↓
Language generation
   ↓
Memory extraction
   ↓
return reply
```

This means the user waits for Memory Extraction before `chat()` returns.

This matters especially after v2.0 because Local language generation is intentionally accepted at a slower latency than cloud generation.

The v2.0 decision therefore leaves:

```text
Memory Extraction → Gemini
```

while v2.1 changes **when it executes**, not necessarily **which provider it uses**.

---

# 3. Primary Objective

Change:

```text
chat()
 ↓
reply
 ↓
memory extraction
 ↓
return
```

into:

```text
chat()
 ↓
reply
 ↓
schedule memory extraction
 ↓
return immediately
```

Background:

```text
Memory Task
    ↓
MemoryExtractor
    ↓
MemoryManager
    ↓
SQLite
```

The user-facing response path must no longer wait for Memory Extraction.

---

# 4. Core Philosophy

> **Response latency and memory persistence are separate concerns.**

Language generation should complete the user interaction.

Memory extraction should continue independently.

Therefore:

```text
Chat Response
    ≠
Memory Persistence
```

---

# 5. Hard Architectural Rules

## Rule 1 — Companion remains the orchestrator

`Companion` may submit/schedule background memory work.

It must NOT become a thread manager containing all memory-worker logic.

## Rule 2 — MemoryExtractor remains responsible for extraction

MemoryExtractor continues deciding:

- whether content is worth remembering;
- what memory content is generated;
- what category is used;
- how extraction is performed.

Do not move extraction logic into a thread class.

## Rule 3 — MemoryManager remains persistence source of truth

The worker must use the existing MemoryManager/persistence path.

Do NOT:

- create another database;
- create another MemoryManager;
- write SQLite directly from GUI;
- create another persistence layer.

## Rule 4 — Background worker is infrastructure, not another AI

Do NOT create:

```text
MemoryAgent
MemoryBrain
MemoryReasoner
```

The worker only executes existing extraction logic asynchronously.

## Rule 5 — Provider selection remains explicit

v2.1 does NOT automatically mean:

```text
Memory Extraction → Local
```

First goal:

> **make existing Memory Extraction asynchronous and safe.**

Only after async execution is stable should Local Memory Extraction be considered.

# 10. Important Ordering Rule

The main response should only be returned after the normal response path is valid.

Preferred:

```text
Generate reply
    ↓
validate reply
    ↓
add assistant reply to Conversation
    ↓
schedule memory extraction
    ↓
return reply
```

Do not schedule extraction before the existing user/assistant conversation state is safely established.

---

# 11. Background Task Input

The task should receive only information actually required by the current MemoryExtractor contract.

Possible inputs may include:

```text
user message
assistant response
relevant context
```

but only if the current extractor requires them.

Do NOT pass entire application objects just for convenience:

```text
Companion
GUI widgets
Vision scheduler
AvatarManager
VoiceManager
whole application state
```

Prefer immutable snapshots/plain values.

---

# 12. Conversation Safety

The worker should not mutate Conversation.

It should not call:

```python
add_user_message()
add_assistant_message()
rollback_last_message()
```

unless inspection proves that this is an existing explicit MemoryExtractor contract.

Memory extraction should observe a stable snapshot of the relevant input.

---

# 13. SQLite Thread Safety

Claude MUST inspect how the current database layer handles SQLite connections.

Do not assume that a connection can safely cross worker threads.

If the existing database layer does not support cross-thread use:

> add the smallest worker-local connection or synchronization boundary compatible with the current design.

Do NOT redesign the database system.


unless an actual architecture blocker makes it necessary.

Do not introduce a new framework merely because asynchronous work exists.

# 29. Shutdown Policy

Application shutdown is critical.

Inspect the current lifecycle and decide whether already-running memory work should finish before shutdown.

Preferred when practical:

```text
already-running extraction
        ↓
finish safely
        ↓
close resources
```

But shutdown must never hang indefinitely.

If a provider/network task is stuck, use a bounded shutdown strategy appropriate to the current architecture.

Do not invent an unrelated application lifecycle system.

---

# 30. Application Exit Safety

A background task must never:

- keep the process alive forever;
- access a destroyed GUI object;
- write after database shutdown;
- use a closed database connection;
- use invalid application state after shutdown.

---

# 31. Exception Handling

Background execution must catch and log failures.

Conceptually:

Use the project's actual logging API.

Do not expose technical traceback to the user.
