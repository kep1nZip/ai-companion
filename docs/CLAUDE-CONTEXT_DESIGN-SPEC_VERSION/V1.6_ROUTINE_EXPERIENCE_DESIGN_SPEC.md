# v1.6 — Routine Experience — Design & Implementation Specification

**Status:** PLANNED — NOT IMPLEMENTED

---

## Overview

Version **v1.6 — Routine Experience** introduces a user-facing GUI experience for the existing Routine System implemented in **v0.8**.

This milestone is focused on **visibility, control, and transparency** of the Routine System.

It is **not** a Routine System rewrite and **not** Routine System v2.

The existing Routine architecture must remain the source of truth.

### Core Rule

> Inspect existing Routine implementation first.  
> Reuse existing architecture second.  
> Extend minimally only when absolutely necessary.

# 2. Objective

Allow the Teacher to:

- View Routine status
- View current routine
- View next scheduled routine
- View cooldown information
- View routine history
- Understand whether a routine is active or suppressed
- Enable or disable Routine execution

Without taking ownership away from the Routine backend.

The GUI must expose Routine functionality safely without duplicating scheduling logic.

---

# 3. Core Philosophy

Routine remains:

> Scheduler + Rules + Event Generator

Routine is **not**:

> A second AI system that generates language.

### Existing Architecture

```text
Clock
  ↓
RoutineScheduler
  ↓
RoutineEngine
  ↓
RoutineEvent
  ↓
Companion
  ↓
ContextBuilder
  ↓
Gemini
  ↓
Arona
```

### GUI Architecture

```text
Routine GUI
      ↓
Routine Public API
```

The GUI observes and controls lifecycle only.

---

# 10. Enable / Disable Lifecycle

Inspect whether the backend already provides:

```python
enable()
disable()
is_enabled()
```

or equivalent APIs.

### If Existing

Reuse them.

### If Missing

Do not redesign the Routine system.

Only add the smallest possible lifecycle boundary required for GUI control.

---

# 11. Disable Semantics

When disabled:

```text
Routine Scheduler
      ↓
     STOP
```

No new RoutineEvents may be generated.

Disabling Routine must never remove:

- History
- Memory
- Relationship state
- Emotion state
- Behavior state

Only future routine evaluation stops.

---

# 12. Re-enable Behavior

Expected lifecycle:

```text
Routine Disabled
      ↓
Enable
      ↓
Scheduler Resumes
```

Missed routines must not be replayed automatically.

Example:

```text
Routine OFF for 3 hours
      ↓
Enable
```

Must not instantly trigger:

- Morning Greeting
- Lunch Reminder
- Water Reminder
- Etc.

Scheduler continues normally from current state.

---

# 13. Persistence Policy

Do not introduce persistence automatically.

Safe default:

```text
Application Start
       ↓
Routine = ENABLED
```

Unless an existing configuration contract already exists.

Do not silently store state in:

- Database
- .env
- Config files

without an existing persistence design.

---

# 14. Schedule Visibility

Allowed UI fields:

- Next Routine
- Next Trigger
- Scheduled Time
- Routine Type

Only if backend APIs already expose them.

Do not build a second schedule generator.

---

# 15. Next Routine Policy

If backend provides:

```python
next_event()
```

Use it.

If backend exposes a queue:

Use the queue.

If backend provides no API:

Display:

```text
Next Routine
Not Available
```

Never duplicate scheduler logic in the GUI.

---

# 16. Cooldown Visibility

Cooldown data must come directly from the backend.

Example:

```text
Drink Water
Ready

Idle Chat
18 Minutes

Morning Greeting
23 Hours
```

The GUI must not own cooldown calculations.

---

# 17. Cooldown Countdown

Presentation-only countdowns are allowed.

Example:

```text
Backend:
Cooldown Until 11:42

GUI:
11:25 → 17 min
11:26 → 16 min
```

Backend timestamps remain authoritative.

---

# 18. Routine History

Read existing RoutineHistory implementation.

Do not create:

```text
RoutineGuiHistory
RoutineHistoryDatabase
```

Use the existing storage mechanism.

If history is memory-only, display memory-only history.

Do not redesign persistence architecture.

---

# 19. History Entries

Display only fields that actually exist.

Potential fields:

- Routine type
- Triggered at
- Completed
- Suppressed
- Skipped
- Reason

If a field does not exist:

Do not fabricate it.

# 20. Suppression Visibility

```text

❌ Force Routine
```

unless supported by a future milestone.

# 27. Threading Policy

- Second Scheduler
- GUI-owned Scheduler
- Duplicate Routine Engine execution

```text

       ↓
RoutineEngine
```

```text

      ↓

```

# 28. Live Updates

Priority order:

1. Existing Qt signals
2. Lightweight polling
3. Never add a global event bus

Polling is acceptable for:

- Countdown displays
- Status refreshes

Polling must never execute Routine logic.

# 35. Acceptance Criteria

## Navigation

- Routine appears in sidebar
- Routine page opens successfully
- Existing pages continue working

## Enable / Disable

- Routine status visible
- Disable stops future evaluation
- Enable resumes lifecycle
- No backlog replay
- History preserved

## Schedule

- Current / next routine displayed when available
- Schedule comes from backend
- No duplicate scheduler

## Cooldowns

- Cooldowns visible when available
- Countdown is presentation-only
- Backend remains authoritative

## History

- History visible
- No new database
- No fabricated entries
- Only real backend fields displayed

## Architecture

- GUI never calls Gemini
- GUI never creates a RoutineEngine
- GUI never creates a Scheduler
- Routine remains Qt-independent
- Companion remains orchestrator

## Regression

Must remain functional:

- Chat
- Memory
- Voice
- Avatar
- Vision
- Initiative
- Developer Tools
- Settings

# 37. STOP Conditions

Stop implementation and request clarification if:

1. Safe enable/disable boundary does not exist
2. Scheduler ownership is unclear
3. GUI requires a second scheduler
4. History requires database redesign
5. Cooldown lacks a public read API

7. GUI requires Gemini
