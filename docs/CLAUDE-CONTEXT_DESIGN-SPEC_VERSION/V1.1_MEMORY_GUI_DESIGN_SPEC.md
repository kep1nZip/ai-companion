# 7. Read-Only Policy

For v1.1, the Memory GUI is read-only.

Allowed:

-   Read recent memories.
-   Search memories.
-   Read memory details.
-   Refresh displayed data.

Not allowed:

-   Create memories.
-   Update memories.
-   Delete memories.
-   Modify memory categories.
-   Modify database schema.

If MemoryManager has write APIs, the Memory GUI must not call them.

# 9. Snapshot / DTO Boundary

Prefer immutable read data between backend and GUI.

Illustrative example:

``` python
@dataclass(frozen=True)
class MemoryItem:
    id: str
    content: str
    category: str
    created_at: datetime
```

And:

``` python
@dataclass(frozen=True)
class MemorySnapshot:
    items: tuple[MemoryItem, ...]
    total: int
```

These are conceptual examples.

Do not invent fields that the actual database/API does not provide.

If a field does not exist, omit it.

Never fabricate memory metadata.

# 18. Threading / Responsiveness

The Memory page must not freeze the GUI.

However, do NOT automatically create a new worker class merely because a
loading state exists.

First inspect the current GUI worker architecture.

If the existing implementation safely supports synchronous reads and
they are demonstrably fast enough, use the simplest correct
implementation.

If asynchronous execution is required, follow the project's existing
worker pattern.

Do not invent a new concurrency architecture.
