# v2.1 — Async Memory Extraction — STATUS: ✅ IMPLEMENTED (pending Teacher runtime test)

## Ringkasan

Memory Extraction tidak lagi memblokir `Companion.chat()`. Sebelumnya
Teacher menunggu DUA panggilan Gemini berurutan (bahasa utama + ekstraksi
memori) sebelum balasan diterima. Sekarang:

```
chat()
  ↓
reply (Local/Gemini)
  ↓
conversation update
  ↓
schedule memory extraction   <-- submit ke background thread, TIDAK menunggu
  ↓
RETURN reply                 <-- Teacher terima balasan di sini
```

Ekstraksi berjalan independen di background:

```
Memory Task (background thread)
  ↓
MemoryExtractor.extract()   <-- TIDAK BERUBAH, tetap Gemini (v2.2 scope)
  ↓
MemoryManager.save_memory() <-- TIDAK BERUBAH, tetap satu-satunya penulis DB
  ↓
SQLite (memory.db)
```

**MemoryExtractor dan MemoryManager TIDAK diubah kontraknya sama sekali** —
cuma cara mereka dipanggil yang berubah (async, bukan inline). Sesuai
prinsip inti spec: *"Async changes timing, not meaning."*

## Keputusan Desain Penting (dan Kenapa)

### 1. `threading.Thread(daemon=True)` + `queue.Queue`, BUKAN `ThreadPoolExecutor`

Percobaan pertama pakai `concurrent.futures.ThreadPoolExecutor(max_workers=1)`
— pilihan stdlib yang wajar dan sempat terlihat cukup. Tapi lewat test
langsung (subprocess, task background yang sengaja dibuat macet 8 detik),
ketahuan `ThreadPoolExecutor` mendaftarkan `atexit` hook GLOBAL
(`concurrent.futures.thread._python_exit`) yang men-join SEMUA worker
thread dari SEMUA executor di proses itu — hook ini tetap jalan terlepas
dari `executor.shutdown(wait=False)` yang sudah dipanggil eksplisit pada
satu instance.

**Bukti test:**
```
shutdown(wait=True, timeout=1.0) dengan task tidur 8 detik
→ shutdown() sendiri return dalam ~1 detik (sesuai timeout) ✅
→ TAPI proses Python secara keseluruhan tetap makan waktu ~8 detik
  sebelum benar-benar exit ❌ (melanggar v2.1 §30: "A background task
  must never keep the process alive forever")
```

Diganti ke `threading.Thread(daemon=True)` + `queue.Queue` — pola yang
SUDAH ADA dan sudah divalidasi di repo ini (`vision/auto_scheduler.py`,
sejak v1.5.2, dengan komentar eksplisit "daemon=True — jaga-jaga kalau
stop() lupa dipanggil, thread tidak menahan proses exit"). Re-test dengan
skenario sama:

```
shutdown(wait=True, timeout=1.0) dengan task tidur 8 detik
→ shutdown() return dalam ~1 detik ✅
→ TOTAL WALL TIME proses: ~1 detik ✅ (bukan ~8 detik)
```

Ini murni penerapan Rule 15/16 spec ("Do not introduce a new concurrency
abstraction if an existing one can safely be reused") — hanya saja baru
ketahuan setelah eksperimen, bukan cuma dari membaca kode.

### 2. `max_workers=1` (satu thread pekerja, bukan pool)

Task selalu jalan berurutan, tidak pernah overlap. Konsekuensinya: kita
tidak perlu membuktikan `MemoryExtractor`/`MemoryManager` aman dipanggil
dari **beberapa** thread background sekaligus (§7) — cukup terbukti aman
dipanggil dari **satu** thread non-GUI. Ini juga otomatis memenuhi Rule 17
("One Task Per Chat") tanpa dedup logic tambahan.

### 3. SQLite thread-safety — tidak perlu redesign apa pun

Inspeksi `database/memory_manager.py`: setiap method (`save_memory`,
`load_memories`, dst) membuka koneksi SQLite baru sendiri lewat
`_connect()` dan menutupnya di akhir `with` block — **tidak pernah**
menyimpan connection sebagai state instance yang dipakai bersama. Karena
tidak ada connection object yang melintasi thread, `check_same_thread`
default sqlite3 tidak relevan di sini. `MemoryManager` aman dipakai apa
adanya dari background thread, tanpa perubahan (§13/§14 — Rule 3
terpenuhi, tidak ada `AsyncMemoryManager`/`MemoryManagerV2`).

### 4. Ordering — ternyata sudah hampir pas dari sononya

Sebelum v2.1, `_remember_if_useful(user_input)` SUDAH dipanggil di posisi
yang benar (setelah `add_assistant_message()`, setelah update
Routine/Initiative, tepat sebelum `return reply`) — cuma sinkron. Jadi
perubahan ordering di `chat()` minimal: cukup ganti isi panggilan dari
"jalankan sekarang" jadi "jadwalkan lalu lanjut", posisi baris tidak
berubah.

### 5. Bounded shutdown, bukan wait tanpa batas

`MemoryExtractionWorker.shutdown(timeout=10.0)` (default, konsisten
dengan angka yang sudah dipakai `VisionAutoScheduler.stop()`) — task yang
sedang jalan diberi kesempatan selesai lewat `thread.join(timeout=...)`,
tapi kalau lewat batas waktu, shutdown tetap lanjut. Karena thread-nya
daemon, proses TIDAK PERNAH menggantung menunggunya walau task itu
akhirnya tidak pernah selesai.

## Keputusan yang Perlu Dikonfirmasi GPT/Teacher

**`check_autonomous_opportunity()` TIDAK dijadwalkan memory extraction —
ini SENGAJA, bukan kelalaian.**

Spec §18 menuliskan diagram "Initiative=YES → ... → reply → schedule
memory extraction" seolah jalur otonom juga memicu ekstraksi. Tapi hasil
inspeksi kode (v1.8–v2.0, sebelum v2.1 disentuh sama sekali) menunjukkan
`check_autonomous_opportunity()` **tidak pernah** memanggil memory
extraction — method ini bahkan tidak menerima parameter `user_input`
sama sekali, karena pada giliran otonom memang tidak ada pesan Teacher
(Arona yang memulai, bukan Teacher).

`MemoryExtractor.extract()` kontraknya eksplisit: membaca SATU PESAN
TEACHER (lihat system prompt di `ai/memory_extractor.py`: *"baca satu
pesan dari Teacher (user)"*). Mengekstrak dari balasan Arona sendiri akan
mengubah makna ekstraksi secara substansial — ini kena Stop Condition #9
("Memory extraction semantics must change substantially").

**Kesimpulan saya:** perilaku ini dipertahankan APA ADANYA (tidak ada
penjadwalan ekstraksi di jalur otonom), sudah didokumentasikan dengan
komentar eksplisit di kode. Acceptance criteria "Autonomous responses
schedule memory extraction" (§46) secara literal TIDAK terpenuhi — tapi
saya percaya ini karena tidak ada yang untuk dijadwalkan, bukan karena
mekanismenya belum siap (mekanismenya sama sekali provider/turn-agnostic,
kalau suatu saat ada Teacher-input di jalur otonom, tinggal panggil
`self._schedule_memory_extraction(...)` yang sama persis). **Mohon
konfirmasi apakah pembacaan ini sesuai maksud GPT**, atau apakah memang
dimaksudkan untuk mengekstrak sesuatu yang lain di jalur otonom.
