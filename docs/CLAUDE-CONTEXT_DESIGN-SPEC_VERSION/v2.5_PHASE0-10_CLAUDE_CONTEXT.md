## Yang Diimplementasikan

### 1. Schema (`database/memory_manager.py`)
- Kolom baru `status` (`"active"` | `"superseded"`), default `"active"` — migration otomatis lewat `PRAGMA table_info()` + `ALTER TABLE ADD COLUMN` (idempoten, aman dipanggil berkali-kali).
- **Diverifikasi nyata**: DB lama (pre-v2.5, tanpa kolom status) dibuat manual lewat SQL mentah, lalu `MemoryManager()` diinstansiasi — migration jalan otomatis, kedua row lama (termasuk 1 row marker internal) otomatis jadi `"active"`.
- `save_memory()` — exact-dedup sekarang cuma dibandingkan terhadap memory `"active"` (memory yang sudah superseded tidak "dihidupkan lagi" tanpa sengaja).
- `load_memories()`/`search_memory()` — default sekarang **active-only** (parameter baru `include_superseded=False`). **Tidak mengubah perilaku** untuk database yang belum pernah punya row `"superseded"` (semua database sebelum v2.5).
- **Baru**: `supersede_memory(old_id, category, content)` — ATOMIC (1 koneksi): tandai lama `"superseded"`, buat baru `"active"`. **Tidak pernah delete** (history preservation, §12 spec).
- **Baru**: `touch_memory(id)` — refresh `updated_at` saja untuk relation DUPLICATE, tanpa menimpa konten.

### 2. Extraction Contract (`ai/memory_extractor.py`)
- Konstanta relation terpusat: `RELATION_NEW/DUPLICATE/UPDATE/SUPERSEDES` + `VALID_RELATIONS` (§6B "jangan sebar magic string").
- `EXTRACTION_SYSTEM_PROMPT` — paragraf hedging/noise/kategori v2.2.1 **tidak diubah satu kata pun**, hanya DITAMBAH instruksi relation-awareness + format output baru.
- `extract(user_input, related_memories=None)` — parameter baru **opsional** (backward-compat penuh — pemanggil lama tanpa `related_memories` mendapat perilaku persis v2.1/v2.2, relation selalu `NEW`).
- Defensive parsing berlapis: relation tidak dikenal → fallback `NEW`; `target_memory_id` invalid/null untuk relation selain NEW → fallback `NEW` (bukan silang-update ke row yang salah).

### 3. Retrieval & Persistence Dispatch (`ai/companion.py`)
- **Baru**: `_select_related_memories_for_extraction()` — reuse struktur `_select_relevant_memories()` yang sudah ada, **ditambah filter marker** (`content.startswith("__ARONA_")`) sesuai temuan kritis Phase 0. `_select_relevant_memories()` lama **tidak disentuh** (dipakai chat context, tetap seperti sebelumnya, sesuai keputusan "no unrelated refactor").
- **Baru**: `_persist_fact(memory_manager, fact)` — module-level, dispatch relation → method `MemoryManager` yang benar (`SUPERSEDES→supersede_memory`, `UPDATE→update_memory`, `DUPLICATE→touch_memory`, `NEW/fallback→save_memory`). Try/except per-fakta (1 fakta gagal tidak menjatuhkan fakta lain).
- `_schedule_memory_extraction()` — retrieval & extraction sekarang **relation-aware**, tetap 100% async (tidak ada pekerjaan baru di jalur sinkron `chat()`).

### 4. Test Infrastructure (`test_memory_quality_validation.py`)
- **Diperluas** (bukan ditulis ulang): `_run_case(..., use_relation=False)` — default **tidak berubah** (explicit_fact/noise/hedging tetap jalur lama persis).
- `use_relation=True` **khusus untuk `CONTRADICTION_SEQUENCE`** — sekarang benar-benar menjalankan pipeline v2.5 penuh (retrieval → extract relation-aware → `_persist_fact`, fungsi produksi yang SAMA, bukan re-implementasi).
- Laporan markdown diperbarui: bagian "Known Issue Contradiction (v2.2.2)" → **"Contradiction — Primary Test v2.5"** dengan verdict tegas ✅ PASS (`len(final_state)==1`) / ❌ FAIL (`>1`), bukan lagi sekadar "dicatat".

## Verifikasi yang Dilakukan (Real, Bukan Simulasi Cerita)

Semua di bawah ini **dijalankan sungguhan** di sandbox pakai mock provider + temporary SQLite DB (sesuai guardrail #16 "test using temporary DB first") — bukan LM Studio/Gemini asli (itu Phase 9, perlu Teacher):

1. **Migration schema dari DB lama** → 2/2 row lama otomatis dapat `status="active"`, termasuk row marker internal — tidak ada yang rusak.
2. **`supersede_memory()`** → atomic, tidak destructive delete, dikonfirmasi lewat assertion `len(all_rows) == len(before)+1` (row lama tetap ada, cuma status berubah).
3. **`MemoryExtractor.extract()` — 5 skenario defensive**: backward-compat tanpa relation, SUPERSEDES terparse benar + related memory masuk ke prompt, target invalid → fallback NEW, relation halusinasi → fallback NEW, JSON rusak → `[]` aman (regresi v2.2.1).
4. **Primary Contradiction Test end-to-end** (`"suka americano"` → `"tidak suka lagi"`): retrieval menemukan memory lama → extractor (mock) putuskan SUPERSEDES → **hasil akhir tepat 1 active memory**, riwayat lama tetap ada dengan `status=superseded`. **Ini kriteria PASS utama v2.5 (§13/§22).**
5. **Regresi kontaminasi marker**: memory `__ARONA_INTERNAL_STATE__`/`__ARONA_ROUTINE_HISTORY__` **tidak lolos** sebagai related memory, sementara memory sah yang kebetulan mengandung kata sama (`"suka Arona"`) **tetap lolos** — filter presisi, tidak overzealous.
6. **DUPLICATE relation** → `touch_memory()`, tidak menambah row, konten asli dipertahankan (bukan ditimpa paraphrase baru).
7. **Backward-compat**: `Companion()` konstruktor lama tanpa parameter apa pun (persis `test_developer_snapshot.py`) tetap construct normal.
8. **Method asli `Companion._select_related_memories_for_extraction()`** (bukan tiruan) diuji langsung via instance Companion — bekerja benar, filter marker aktif.
9. **Wiring `test_memory_quality_validation.py`** — `_run_case(use_relation=True)` dites langsung lewat scripted mock provider, hasil `contradiction_final_state` tepat 1 entri, PERSIS logic yang akan jalan saat Teacher run dengan Gemini/Local asli.
10. **Regresi eksplisit**: explicit_fact/noise/hedging (`use_relation=False`, default) — 3/3 case tetap `passed=True` dengan `saved_count` yang sama seperti sebelum v2.5, mengonfirmasi jalur lama benar-benar tidak berubah.

## Catatan & Keterbatasan

1. **Phase 8 (Update) belum ada test terpisah eksplisit.** Jalur kode UPDATE (`memory_manager.update_memory()`) sudah ada sejak sebelum v2.5 dan sudah dipakai lewat `_persist_fact`, tapi saya belum membuat skenario test spesifik ("Aku tinggal di Bandung" → "Sekarang di Jakarta" dst.) seperti SUPERSEDES. **Rekomendasi:** tambahkan ke `CONTRADICTION_SEQUENCE`-style test case terpisah kalau Teacher mau memvalidasi ini eksplisit — secara struktural kodenya sudah siap (dispatch `UPDATE` sudah ada), cuma belum ada bukti empiris skenario UPDATE spesifik.
2. **Phase 9 (Gemini + Local asli) belum dijalankan** — saya tidak punya akses LM Studio/Gemini API nyata di sandbox. `test_memory_quality_validation.py` sudah siap jalan (`python test_memory_quality_validation.py`), tinggal Teacher eksekusi.
3. **Kontaminasi marker ke chat context** (temuan Phase 0 §5 — BUKAN bagian retrieval extraction yang baru, tapi jalur lama `_select_relevant_memories()`) **sengaja tidak diperbaiki** di v2.5 ini, sesuai rekomendasi (b) yang saya ajukan sebelumnya dan tidak dibantah — dicatat sebagai **known issue terpisah**, bukan bagian scope v2.5.
4. **Tidak ada mass migration** — seluruh memory lama Teacher (kalau ada) otomatis jadi `"active"` lewat schema migration, **tidak ada satu pun yang otomatis di-supersede** oleh v2.5 ini sendiri (§20 spec).
