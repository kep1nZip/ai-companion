# V3.5 — Temporal Awareness & Task Continuity

## 0. Milestone Identity

**Version:** v3.5  
**Name:** Temporal Awareness & Task Continuity  
**Status:** PLANNED  
**Previous milestone:** v3.4 — Memory Relevance Ranking & Context Quality  
**Primary goal:** Make Arona better at understanding time-sensitive conversation context and continuing ongoing work naturally, while avoiding a new Task Manager, planner, semantic classifier, or persistent task database.

---

# 1. Why V3.5

The current architecture already provides several useful temporal signals:

- `ContextBuilder` already exposes the current date/time.
- v3.1 already exposes conversation continuity based on elapsed idle time.
- v3.3 already handles reference cues such as "yang tadi", "kemarin", and similar follow-ups.
- v3.4 already ranks retrieved memories and protects context from weak/generic matches.
- Routine already owns calendar-like recurring reminders.
- Initiative already decides whether autonomous speech may start.

v3.5 must NOT replace any of those systems.

The goal is to connect the existing pieces more coherently around one problem:

> **What is happening in the conversation over time, and is Teacher continuing, pausing, returning to, or explicitly finishing an ongoing activity?**

The desired result is not a task-management system.

It is a **better temporal context signal** for the existing LLM.

---

# 2. Core Principle

v3.5 should provide **evidence**, not make semantic decisions.

The application may reliably say:

```text
- Current time is 10:30 WIB.
- Teacher used the phrase "besok".
- Teacher used an explicit completion cue: "sudah selesai".
- Teacher used a continuation cue: "masih", "lanjut", "belum".
- Teacher returned after a long idle gap.
- The existing v3.3 anchor is LeadEstate.
```

The application must NOT fabricate:

```text
- Task is definitely still active.
- Teacher's deadline is definitely tomorrow.
- Teacher abandoned task X.
- Teacher's current priority is task Y.
- Teacher finished the project.
```

Those semantic interpretations remain the responsibility of the conversational model using the supplied evidence.

---

# 3. Architectural Position

v3.5 is a **context-signal layer**.

```text
                     Teacher message
                           │
                           ▼
                    ┌──────────────┐
                    │   Companion  │
                    └──────┬───────┘
                           │
          ┌────────────────┼─────────────────┐
          │                │                 │
          ▼                ▼                 ▼
   v3.3 Reference    v3.4 Memory       v3.5 Temporal
      Signals          Ranking            Signals
          │                │                 │
          └────────────────┼─────────────────┘
                           ▼
                   Context / LLM
                           │
                           ▼
                     Arona response
```

No second orchestrator is introduced.

# 6. Phase 1 — Temporal Signal Detection

Create one lightweight, deterministic temporal signal layer only if Phase 0 shows the current code does not already provide the needed signals.

Conceptual examples:

```text
hari ini
sekarang
tadi
barusan
kemarin
besok

minggu lalu
bulan depan
bulan lalu
baru saja
sebentar lagi
masih
belum
sudah
selesai
lanjut

```

The implementation should prefer explicit patterns over large word dictionaries.

The detector should return **signals**, not semantic conclusions.

Example:

```python
TemporalSignals(
    relative_time_terms=["besok"],
    continuation_cues=["lanjut"],
    unfinished_cues=["masih"],
    completion_cues=[],
)
```

Do not return:

```python
task_status="active"
deadline="tomorrow"
```

unless the information is explicitly stated and the representation is strictly evidence-based.

# 7. Phase 2 — Relative Date Normalization

For unambiguous relative date expressions, the application may calculate the corresponding calendar date using the existing timezone configuration.

Examples:

```text
"hari ini"
"besok"
"lusa"
"kemarin"
```

Given:

```text
Current date: 29 September 2026
```

deterministic normalization can produce:

```text
hari ini → 29 September 2026
besok    → 30 September 2026
lusa     → 1 October 2026
kemarin  → 28 September 2026
```

This is acceptable because it is ordinary date arithmetic.

Do NOT normalize vague expressions into fabricated exact dates:

```text
nanti
sebentar
suatu saat
kayaknya minggu depan
```

For vague expressions, retain only the raw signal.

---

# 8. Phase 3 — Temporal Reference vs V3.3 Reference Resolution

v3.5 MUST NOT replace v3.3 reference resolution.

Example:

```text
"lanjut yang kemarin"
```

v3.3 asks:

> What previous conversation topic does "yang kemarin" refer to?

v3.5 may add:

> Teacher explicitly used the temporal cue "kemarin".

Both pieces can be supplied to the LLM.

The application must NOT combine them into a fabricated semantic conclusion such as:

```text
"Teacher definitely means the LeadEstate task from yesterday."
```

unless that exact relationship is explicit in available deterministic data.

```text

```

Those are semantic/task-management conclusions.

# 23. Important Ambiguity Rule

Temporal cues can themselves be ambiguous.

For example:

```text
"nanti"
"sebentar"
"bentar lagi"
"kapan-kapan"
```

The application MUST NOT invent exact timestamps.

Likewise:

```text
"minggu depan"
```

may be normalized only if the phrase is unambiguous enough for ordinary calendar arithmetic.

If the language is genuinely vague, preserve it as a raw temporal cue and let the LLM interpret it.
