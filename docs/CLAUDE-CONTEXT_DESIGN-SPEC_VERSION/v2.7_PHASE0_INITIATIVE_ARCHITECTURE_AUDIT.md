## 1. Initiative Source Map

```
Companion.chat()                          (Teacher kirim pesan)
    -> _update_behavior(user_input)       -> BehaviorEngine.update() -> InternalStateCoordinator.process_message()
                                              *** MEMBUAT InternalState BARU, timestamp di-reset ke now() ***
    -> Vision.get_context()               (freshness-gated sejak v1.5.2, None kalau stale/off)
    -> Routine.update(behavior, vision)   -> RoutineEvent | None
    -> Initiative.update(behavior, vision, routine_event)
           -> InitiativeHistory.in_cooldown() / budget_exceeded()   [HARD GATE, sebelum scoring]
           -> InitiativeEngine.compute()
                  -> check_suppression(vision, is_voice_active, is_actively_typing)  [HARD GATE kedua]
                  -> DecisionContext(idle_seconds, behavior_state, vision_context, routine_event, hour)
                  -> for rule in DEFAULT_RULES: score += rule.weight (kalau match)
                  -> decide(score, threshold, reasons)
    -> _build_contents(...)               (chat berjalan seperti biasa, TIDAK terpengaruh decision_result)

Companion.check_autonomous_opportunity()  (dipanggil QTimer GUI tiap 60 detik, TANPA pesan Teacher)
    -> current_behavior_state()           *** READ-ONLY, TIDAK reset InternalState.timestamp ***
    -> Vision.get_context()               (sama seperti di atas)
    -> Routine.update(...)                (sama)
    -> Initiative.update(...)             (sama persis alur di atas)
    -> if decision_result.should_start:
           _build_autonomous_contents(...) -> provider.generate() -> Voice/Avatar
       else:
           return None (Arona diam, hasil valid & diharapkan)
```

**Titik krusial yang dikonfirmasi lewat trace kode (bukan asumsi):** `InternalState.timestamp` **hanya di-reset saat Teacher benar-benar mengirim pesan** (`chat()` → `_update_behavior()` → `process_message()` → construct `InternalState` baru). Jalur autonomous (`check_autonomous_opportunity()`, dipanggil QTimer tiap 60 detik) memakai `current_behavior_state()` yang **murni membaca properti**, TIDAK PERNAH memanggil `process_message()`. **Artinya `idle_seconds` yang dipakai `IdleRule` SUDAH secara akurat merepresentasikan "detik sejak pesan terakhir Teacher"** — bukan "detik sejak evaluasi Initiative terakhir".

## 2. Phase 2 (Cooldown) — SUDAH LENGKAP, Tidak Perlu Dikerjakan Ulang

`initiative/initiative_history.py` (`InitiativeHistory`) + `initiative/initiative.py` (`Initiative.update()`) sudah punya:
- **Cooldown** (`cooldown_minutes: float = 45.0`) — dicek SEBAGAI HARD GATE **sebelum** scoring jalan sama sekali (`in_cooldown()` di awal `update()`), persis alur konseptual spec §8 ("Autonomous response → Cooldown begins → Routine trigger → Initiative rejects → Cooldown expires → Initiative may evaluate again").
- **Budget per jam & hari** (`max_per_hour=3, max_per_day=10`) — hard gate kedua, sebelum scoring.
- **Persisten** lewat `save_by_marker`/`load_by_marker` (marker `__ARONA_INITIATIVE_HISTORY__`) — bertahan lintas restart aplikasi.
- **Observable** lewat `get_remaining_budget()`, `get_cooldowns()` — sudah tersambung ke `InitiativeSnapshot` (lihat §6).

**Catatan soal angka 45 menit / 3 per jam / 10 per hari:** ini adalah default YANG SUDAH ADA dari versi sebelumnya (bukan saya pilih sekarang), jadi tidak melanggar guardrail v2.7 "Jangan memilih angka cooldown arbitrer" (guardrail itu berlaku untuk keputusan BARU, bukan retroaktif ke keputusan lama). **Tapi** relevan dicatat: sekarang Teacher sudah punya Developer Dashboard (`InitiativeSnapshot` sudah menampilkan cooldown/budget real-time, dan v2.6 sudah menambah observability Context) — kalau Teacher merasa 45 menit/3x/10x tidak pas setelah lihat pola pemakaian nyata, itu tinggal parameter constructor yang sudah ada, tidak perlu kode baru.

**Rekomendasi: Phase 2 TIDAK perlu dikerjakan ulang.** Sudah PASS.

## 3. Phase 1 (Recent Interaction) — Gap Nyata di Balik Implementasi yang Sudah Ada

`IdleRule` (`initiative_rules.py`) memberi **bonus +20** kalau `idle_seconds >= 900` (15 menit). Ini FUNGSIONAL berarti: baru saja chat → `idle_seconds` kecil → TIDAK dapat bonus +20. Secara tidak langsung ini SUDAH membuat skor "baru saja interaksi" lebih rendah dari "sudah lama idle".

**Tapi ini bukan PENALTY eksplisit — cuma ABSENSI bonus.** Masalahnya: rule lain bisa saja menjumlah ke threshold TANPA butuh kontribusi IdleRule sama sekali. Contoh nyata dari `DEFAULT_RULES` + `DEFAULT_THRESHOLD=50.0`:
```
RoutinePendingRule   +25  (ada event apa pun)
RelationshipRule     +15  (relationship average >= 60)
MoodBonusRule        +10  (mood positif)
                     ---
                     +50  == threshold, TERCAPAI tanpa IdleRule sama sekali
```
**Artinya:** kalau Teacher baru saja kirim pesan 5 detik lalu, lalu 60 detik kemudian ada routine event + relationship dekat + mood bagus, Initiative BISA langsung `should_start=True` — persis skenario spam yang ingin dicegah spec (§7 Goal C: "jangan langsung autonomous speak lagi").

**Ini temuan paling actionable dari seluruh audit** — bukan spekulasi, tapi kombinasi angka nyata dari `DEFAULT_RULES` yang sudah ada.

**Rekomendasi Phase 1 v2.7:** tambah SATU rule baru eksplisit (`RecentInteractionPenaltyRule` atau serupa) yang memberi PENALTY (bukan cuma absensi bonus) kalau `idle_seconds` di bawah ambang pendek (mis. beberapa menit) — reuse `idle_seconds` yang SUDAH ada di `DecisionContext`, TIDAK perlu state baru. Ambang & besar penalty harus diukur, bukan ditebak (selaras guardrail #20 "Measure before tuning scores").

## 4. Phase 3 (Opportunity Relevance) — Gap Nyata: Priority Data Ada, Tidak Dipakai

`RoutinePendingRule.evaluate()`:
```python
if ctx.routine_event is not None:
    return f"Ada routine event pending: {ctx.routine_event.event_type.value}"
```
Selalu **+25 flat**, apa pun `event_type`-nya. Padahal `RoutineEvent.priority` (`EventPriority`: LOWEST..CRITICAL) **SUDAH ADA sebagai field**, dan `routine/routine_rules.py::_PRIORITY` **sudah memetakan priority per event type** (`MORNING_GREETING=MEDIUM`, `IDLE_CHAT=LOWEST`, dst) — data itu SAMPAI ke `RoutineEvent` yang diterima Initiative, tapi **diabaikan sepenuhnya** oleh `RoutinePendingRule`.

**Ini match langsung dengan Goal A spec** ("more signals ≠ always higher score" — dalam hal ini, sebaliknya: signal priority SUDAH ADA tapi tidak dipakai sama sekali). Fix-nya kecil dan rendah risiko: `RoutinePendingRule` baca `ctx.routine_event.priority` dan skalakan weight sesuai (mis. LOWEST → weight lebih kecil, CRITICAL → weight lebih besar) — reuse data existing, tidak ada state/sistem baru.

## 5. Phase 5 (Memory-Aware Initiative) — Gap Nyata, Perlu Keputusan Desain

`initiative_rules.py::DecisionContext` (dataclass frozen):
```python
idle_seconds: float
behavior_state: BehaviorState
vision_context: Optional[VisionContext]
routine_event: Optional[RoutineEvent]
hour: int
```
**Nol field terkait Memory.** `Initiative`/`InitiativeEngine` tidak pernah punya akses ke `MemoryManager` untuk keperluan relevansi (hanya untuk persistence history di `InitiativeHistory`, beda tujuan).

**Tantangan desain nyata (bukan sekadar "tambah field"):** mekanisme retrieval memory yang sudah ada (`Companion._select_relevant_memories()`) butuh **teks query** (pesan Teacher) untuk dicari — tapi saat `check_autonomous_opportunity()` berjalan, **tidak ada pesan Teacher baru sama sekali** (itu keseluruhan poin autonomous check). Jadi "apa yang jadi query pencarian memory" harus diputuskan eksplisit.

**Opsi yang match langsung dengan contoh Goal D/Phase 5 di spec** ("Vision: Teacher membuka game X" + "Memory: Teacher pernah suka game X"): pakai **`vision_context.summary`/`application`** (kalau Vision aktif & fresh) sebagai teks query ke mekanisme retrieval yang SUDAH ADA — bukan membangun retrieval baru (guardrail #18 eksplisit melarang "second memory retrieval system"). Kalau Vision tidak aktif/kosong, tidak ada query yang masuk akal → rule ini simply tidak berkontribusi (bukan dipaksakan).

**Rekomendasi:** Companion meneruskan hasil retrieval (list Memory relevan terhadap ringkasan Vision saat ini, reuse `_select_relevant_memories` yang sudah ada) sebagai field baru `DecisionContext.relevant_memory_count` (atau serupa, angka ringkas) — BUKAN daftar Memory penuh (Initiative tidak butuh isi teksnya, cuma butuh tahu "ada/tidak ada, seberapa banyak").

## 6. Phase 6 (Vision-Aware Initiative) — Suppression Sudah Ada, Booster Belum

**Sudah ada** (`vision/vision_signals.py`, dipakai bareng oleh Routine dan Initiative): `matches_presentation()`/`matches_focused_work()` — suppression HARD OVERRIDE kalau Vision mendeteksi meeting/coding/dst. Ini PERSIS Goal B ("Vision dapat menjadi salah satu input, tetapi Vision tidak boleh langsung memulai percakapan" — sudah begitu, Vision cuma bisa MENOLAK, tidak bisa MEMULAI).

**Vision OFF/stale sudah otomatis aman** — `vision_context=None` (baik karena OFF maupun karena stale, keduanya sudah di-gate di `Vision.get_context()` sejak v1.5.2/v2.6) membuat kedua fungsi signal itu langsung `return False` — tidak ada cabang kode terpisah yang perlu ditambahkan, ini FREE dari arsitektur yang sudah ada.

**Yang belum ada:** Vision sebagai **booster relevansi** (bukan cuma suppressor) — Goal D & Phase 3 contoh ("Vision menunjukkan game yang pernah disebut" → relevance NAIK, bukan cuma "tidak military ditolak"). Ini natural digabung dengan Phase 5 (§5 di atas) — sinyal yang sama (ringkasan Vision dipakai untuk cari Memory relevan) sekaligus menjawab Phase 5 dan Phase 6 booster.

## 8. Phase 7 (Interruption Cost) — Rekomendasi: JANGAN Tambah Formula Baru

Spec menawarkan formula konseptual (Opportunity + Context + Relationship − Recent Interaction − Cooldown − Interruption Cost), tapi eksplisit memperingatkan: **"Formula final tidak boleh dianggap final sebelum audit dan baseline"** dan **"Jangan membuat 10+ faktor hanya agar terlihat sophisticated."**

Desain SAAT INI (Cooldown+Budget = hard gate terpisah, Suppression = hard override terpisah, baru scoring rule-based di lapisan ketiga) **sudah menerapkan prinsip yang sama** — interruption cost yang PALING TINGGI (meeting, coding, voice aktif, mengetik aktif) sudah ditangani sebagai binary suppression (all-or-nothing), bukan angka minus yang bisa "dikompensasi" oleh rule lain. Ini justru LEBIH AMAN dari formula subtraktif spec (kalau interruption cost cuma pengurang skor, teorinya bisa "dikalahkan" skor tinggi dari rule lain — padahal meeting/coding harusnya TIDAK BOLEH diinterupsi apa pun skornya).

**Rekomendasi: Phase 7 TIDAK perlu ditambah formula baru.** Desain suppression binary yang sudah ada justru lebih sesuai prinsip "protect Teacher's attention" dibanding formula subtraktif yang diusulkan spec sebagai "conceptual" (spec sendiri bilang itu bukan final).
