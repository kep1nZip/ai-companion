# V3.9 — Adaptive Context Budget & Attention Allocation

## 0. Milestone Identity

**Version:** v3.9  
**Name:** Adaptive Context Budget & Attention Allocation  
**Status:** PLANNED  
**Previous milestone:** v3.8 — Context-Aware Initiative & Proactive Support  
**Primary goal:** Make the increasingly rich Arona context pipeline more efficient and focused without arbitrarily deleting information, introducing a second reasoning system, or rebuilding the existing memory/conversation architecture.

---

# 1. Why V3.9

The current intelligence stack has grown substantially:

```text
v3.2 → Memory Quality
v3.3 → Contextual Recall
v3.4 → Memory Relevance Ranking
v3.5 → Temporal Awareness & Task Continuity
v3.6 → Response Calibration
v3.7 → Conversational Feedback & Repair
v3.8 → Context-Aware Initiative
```

The next problem is not necessarily that Arona lacks context.

The problem may become:

> **There is now enough context that some turns may contain more evidence than the model actually needs.**

The intended flow is:

```text
Many available signals
        ↓
Measure
        ↓
Remove empty / redundant pieces
        ↓
Respect context priority
        ↓
Keep the strongest useful evidence
        ↓
Existing LLM
```

V3.9 is therefore an **efficiency and attention-allocation milestone**, not a new intelligence subsystem.

---

# 2. Core Principle

## 2.1 Measure Before Limiting

Do NOT assume that context must be capped.

V3.9 must first establish:

```text
How large is the context?
What part of it grows?
Which sections are usually empty?
Which sections are redundant?
Does larger context actually hurt latency or quality?
```

If the answer is:

```text
Context is still small enough
AND
quality remains good
AND
latency remains acceptable
```

then:

> **No new cap is required.**

That is a valid PASS outcome.

---

## 2.2 Context Availability ≠ Context Necessity

A signal being available does not mean it should always be injected.

Examples:

```text
No temporal cue
→ no Temporal Context

No feedback
→ no Conversation Feedback

No response-style cue
→ no Response Calibration section

No relevant memory
→ no memory block

No active anchor
→ no anchor-specific explanation
```

Empty sections must not be generated merely for completeness.

---

## 2.3 Attention Priority

When multiple context sources exist, priority must remain based on usefulness.

Default conceptual priority:

```text
Tier 1
Current Teacher message + immediate conversation
        ↓
Tier 2
Active reference / current topic
        ↓
Tier 3
Strongly relevant memory
        ↓
Tier 4
Temporal / feedback / calibration / situational evidence
        ↓
Tier 5
Older conversational history
```

This is a conceptual model.

**Phase 0 MUST inspect the current assembly order before changing it.**

Do not arbitrarily reorder the entire context pipeline.

# 4. Hard Boundaries

## 4.1 No Second LLM

Do NOT introduce:

```text
context summarizer LLM
context compression LLM
attention-ranking LLM
memory-selection LLM
```

---

## 4.2 No Vector Database

Do NOT introduce:

```text
FAISS
Chroma
Pinecone
Milvus
Weaviate
```

or any vector infrastructure.

---

## 4.3 No Embedding Pipeline

Do NOT add embedding models just to solve context size.

V3.4 already provides deterministic memory relevance ranking.

---

## 4.4 No RAG Framework

Do NOT turn the context system into a generic RAG architecture.

Existing memory retrieval remains the source.

---

## 4.5 No Conversation Database

Do NOT persist all conversation history merely to enable context budgeting.

The existing `Conversation` remains the owner of current conversation history.

---

## 4.6 No New Memory System

Do NOT create:

```text
ContextMemory
ContextCacheDatabase
ContextSummaryStore
```

unless a future milestone explicitly designs persistent conversation summaries.

V3.9 is not that milestone.

---

## 4.7 No Destructive Memory Behavior

Context budgeting must never:

- delete memory
- change memory status
- supersede memory
- mutate stored memory text

Context selection is temporary.

---

## 4.8 No Provider-Specific Context Logic

Local and Gemini must receive the same application-generated context selection.

Do NOT add:

```python
if provider == "local":
    ...
```

for context budgeting.

Provider performance may differ, but application-side selection must remain provider-agnostic.

---

## 4.9 No Initiative Rewrite

V3.8 already made Initiative context-aware.

V3.9 should not redesign Initiative scoring.

At most, V3.9 may provide better observability about the context that Initiative consumed, if Phase 0 proves that this is useful.

# 10. Phase 5 — Adaptive History Budget

History is currently allowed to remain unbounded when measurements justify it.

V3.9 may introduce or modify a history cap only if:

```text
history grows materially
AND
context cost becomes significant
AND
quality is still recoverable after selection
```

The decision must be evidence-based.

Do NOT use arbitrary values such as:

```text
last 10
last 20
last 50
```

without a baseline.

# 11. Safe History Selection Rules

If a history cap becomes necessary:

## 11.1 Preserve the Current Turn

Always preserve:

```text
current Teacher message
```

---

## 11.2 Preserve Immediate Context

The most recent conversational turns should remain the highest priority.

---

## 11.3 Preserve Reference Dependencies

Do not truncate history in a way that breaks:

```text
"yang tadi"
"yang kemarin"
"itu"
"lanjut yang tadi"
```

when the referenced turn is otherwise necessary for resolution.

---

## 11.4 Preserve Conversation Pairs

Where possible, do not split:

```text
Teacher turn
+
Arona response
```

arbitrarily.

If the architecture already has a safe pair/group boundary, reuse it.

---

## 11.5 Do Not Randomly Drop Messages

Never use random truncation.

# 33. PASS / CONDITIONAL PASS / FAIL

## PASS

Use when:

- context remains coherent;
- unnecessary context is removed;
- latency remains acceptable;
- reference/memory/temporal/feedback/calibration behavior is preserved;
- Local and Gemini share the same context selection;
- no new architecture is introduced unnecessarily.

A valid PASS may explicitly state:

> History cap not enabled because measurement did not justify it.

---

## CONDITIONAL PASS

Acceptable when:

- context optimization is structurally correct;
- minor provider-level wording differences exist;
- a known limitation remains but does not compromise reference/context quality.

---

## FAIL

Hard failures:

- arbitrary history cap introduced without measurement;
- reference resolution regresses;
- relevant memory is removed while irrelevant context remains;
- temporal/feedback/calibration evidence disappears unexpectedly;
- stale Vision enters context;
- Initiative evidence regresses;
- second LLM appears;
- vector/RAG infrastructure is added;
- stored memory is deleted/mutated as part of budgeting;
- provider-specific context selection appears;
- significant context-related latency/regression appears.
