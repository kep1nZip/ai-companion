## 3. Apa yang Diimplementasikan

### Schema (`database/memory_manager.py`)
- Kolom baru `status` (`"active"`/`"superseded"`), migration otomatis dari DB lama (diverifikasi nyata: DB pre-v2.5 tanpa kolom status berhasil di-migrate tanpa kehilangan data).
- `supersede_memory()` — atomic, non-destructive (row lama tidak dihapus, cuma status berubah).
- `touch_memory()` — untuk relation DUPLICATE, refresh recency tanpa menimpa konten.
- `load_memories()`/`search_memory()` — default sekarang active-only (tidak mengubah perilaku DB yang belum pernah punya row superseded).

### Extraction Contract (`ai/memory_extractor.py`)
- Relation constants terpusat (`RELATION_NEW/DUPLICATE/UPDATE/SUPERSEDES`).
- Prompt v2.2.1 (hedging/noise) **tidak diubah satu kata pun** — hanya ditambah instruksi relation-awareness.
- `extract()` menerima `related_memories` opsional — backward-compat penuh.
- **Direvisi 2x** berdasarkan evidence nyata (lihat §5).

### Retrieval & Persistence (`ai/companion.py`)
- `_select_related_memories_for_extraction()` — reuse retrieval yang sudah ada, ditambah filter marker internal (`__ARONA_...`) supaya state internal 4 subsystem lain (Routine/Initiative/InternalState/Relationship) tidak pernah salah tertangkap sebagai kandidat UPDATE/SUPERSEDES.
- `_persist_fact()` — dispatch relation ke method `MemoryManager` yang benar, error-isolated per fakta.

### Test Infrastructure (`test_memory_quality_validation.py`)
- Diperluas (bukan ditulis ulang) — jalur `explicit_fact`/`noise`/`hedging` tidak berubah, jalur `contradiction` sekarang menjalankan pipeline v2.5 penuh dan memberi verdict tegas (PASS/INCOMPLETE), bukan lagi "record only" ala v2.2.2.

## 5. Investigasi Anomali Gemini (2 Iterasi Fix)

**Fix #1 (setelah Run 1):** menambah paragraf instruksi eksplisit — "kalau relation DUPLICATE/SUPERSEDES, tetap wajib keluarkan entri, jangan array kosong." **Hasil Run 2: masih gagal, identik dengan Run 1.**

**Kemungkinan penyebab fix #1 tidak berhasil** (saya tidak bisa memastikan tanpa akses Gemini langsung):
- (a) Instruksi tertulis abstrak kadang tidak cukup kuat untuk mengubah perilaku model — LLM sering merespons lebih baik ke **contoh konkret** daripada aturan naratif.
- (b) File yang dijalankan Teacher di Run 2 mungkin belum memuat fix #1 (tidak bisa saya verifikasi dari sandbox).

**Fix #2 (baru saja saya terapkan, BELUM divalidasi):** menambahkan **contoh konkret** persis skenario yang gagal — termasuk potongan "Output yang SALAH untuk kasus di atas: `[]`" secara eksplisit, supaya model tidak bisa lagi menafsirkan ambigu. Ditambahkan di `ai/memory_extractor.py::EXTRACTION_SYSTEM_PROMPT`, paragraf hedging v2.2.1 tetap tidak disentuh.

**Penting dicatat:** dugaan akar masalah TETAP dugaan, bukan fakta terverifikasi — saya tidak punya cara melihat reasoning internal Gemini. Yang saya tahu pasti (dari kode `ai/gemini.py`): respons `[]` bukan hasil safety-block atau error (kalau itu terjadi, `finish_reason` akan ter-log dan test akan menunjukkan `Error: ...`, bukan `Actual: []` dengan `Error: None`) — jadi ini keputusan eksplisit model, bukan kegagalan teknis di sisi kita.

## 6. Analisis: Apakah Ini FAIL atau Bukan?

Menurut kriteria eksplisit spec v2.5:

- **§24 FAIL** didefinisikan sebagai *"Primary contradiction masih menghasilkan **dua** active memory"* — yang terjadi di Gemini adalah **nol** active memory, kondisi yang berbeda dan tidak secara harfiah masuk kriteria FAIL manapun.
- **§23 CONDITIONAL PASS** eksplisit mengizinkan *"relation model bekerja untuk kasus utama tetapi belum sempurna pada seluruh... provider... semua limitation harus dicatat eksplisit."*
- Tidak ada corruption, tidak ada crash, tidak ada silent fallback, tidak ada regresi ke baseline v2.2.1 (hedging/noise/explicit_fact tetap 100% bersih di Gemini, di KEDUA run).

**Kesimpulan saya: ini CONDITIONAL PASS, bukan FAIL** — tapi dengan catatan bahwa untuk salah satu dari 2 provider wajib (§16), fitur utama v2.5 belum terbukti bekerja setelah 2 percobaan.
