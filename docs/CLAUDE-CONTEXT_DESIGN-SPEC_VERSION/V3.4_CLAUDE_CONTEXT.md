## 3. Alasan Setiap Perubahan

### File baru — `ai/memory_ranking.py`
**Alasan:** spec §20 eksplisit menyarankan modul terpisah kalau memang dibutuhkan ("only if Phase 0 proves a separate utility is justified") — dan memang dibutuhkan: ranking harus pure/testable-in-isolation (spec §20), terpisah dari orchestrator `Companion`.

**Isi:**
- `score_memory(memory, keywords, raw_query_text="")` — skor deterministik. Bobot (didokumentasikan lengkap di code comment sesuai spec §6):
  - `50.0 × exact_phrase` — seluruh `raw_query_text` cocok verbatim sebagai substring (spec §5.3).
  - `4.0 × match_weight_sum` — total PANJANG huruf semua keyword yang match. Kata lebih panjang = lebih spesifik (implementasi konkret §11.2 "Specific beats generic" TANPA kamus entity apa pun).
  - `8.0 × match_count` — jumlah keyword BERBEDA yang match (spec §5.2/§11.3).
  - `5.0 × coverage` — proporsi keyword yang match.
  - **Recency SENGAJA TIDAK dilebur ke skor ini** (lihat catatan bug di §5).
- `rank_memories(memories, keywords, raw_query_text="")` — sort deterministik, tie-break bertingkat: skor → `updated_at` (lebih baru menang) → `id` ascending (final fallback, spec §7 persis).
- `rank_and_select(memories, keywords, limit, raw_query_text="")` — gabungan rank+trim+top_score, dipakai `Companion` sekali saja (spec §16: "avoid ranking the same candidate multiple times").
- `RetrievalOutcome` (NamedTuple) — bentuk return baru `_search_memories_by_keywords()`, membawa `candidate_count`/`duplicates_removed`/`top_score` untuk observability tanpa hitung ulang di tempat lain.

### `ai/companion.py`
1. `_search_memories_by_keywords()` — sekarang mengumpulkan pool kandidat lebih besar (`MEMORY_CANDIDATE_POOL_LIMIT=30`, konstanta baru di `config/constants.py`) SEBELUM diranking dan dipangkas ke budget final (`EPHEMERAL_CONTEXT_MEMORY_LIMIT=10`, TIDAK BERUBAH — kontrak eksternal ke LLM tetap sama besar, cuma isinya sekarang hasil ranking bukan insertion-order).
2. `_select_relevant_memories()` — 3-tier v3.3 (current_message/conversation_anchor/vision_context) TIDAK berubah strukturnya, cuma sekarang meneruskan `raw_query_text` yang sesuai ke tiap tier untuk exact-phrase bonus, dan mencatat metadata ranking baru.
3. `_record_recall()` + `get_memory_decision_debug_snapshot()` — field baru: `candidate_count`, `duplicates_removed`, `top_score`, `top_match_preview` per recall, plus `last_ranking` (ringkasan format persis contoh dashboard spec §12).

### `developer/developer.py` + `ui/developer.py`
Card **"Memory Decisions"** yang sudah ada (v3.2) diperluas — **BUKAN card/dashboard baru** (spec §13 eksplisit melarang "Memory Ranking Dashboard" terpisah) — dengan blok "Memory Ranking (recall terakhir)" menampilkan Candidates/Ranked/Selected/Duplicates Removed/Query Source/Top Score/Top Match, plus detail per-recall di "Recent Recalls".

## 4. Bug yang Ditemukan & Diperbaiki Selama Implementasi (Penting)

Draft awal `score_memory()` meleburkan recency sebagai epsilon kecil (`updated_at.timestamp() / 1e15`) langsung ke skor — **TAPI** `Memory.updated_at` di `database/memory_manager.py` disimpan sebagai **string ISO 8601**, bukan objek `datetime`. Kode awal salah asumsi tipe, memanggil `.timestamp()` pada string (AttributeError), tertangkap diam-diam oleh `except`, sehingga recency **selalu bernilai 0** — bug ini ketahuan sendiri lewat test T04 (Recency Tie-Break) yang gagal saat pertama dijalankan.

**Perbaikan:** bukan cuma menambal parsing string (`_parse_timestamp()` dengan `datetime.fromisoformat()`), tapi sekaligus **memisahkan recency dari skor** — dipakai sebagai tie-break eksplisit tingkat kedua di `rank_memories()` (bukan epsilon yang dijumlahkan), persis urutan tie-break yang diminta spec §7. Ini desain yang lebih kuat: recency dijamin TIDAK PERNAH bisa "menyelinap" memengaruhi urutan lewat kombinasi floating point, sesuai spec §5.5 ("Recency MUST NOT automatically overpower topical relevance") secara lebih ketat daripada rencana awal.

Setelah perbaikan, T04 PASS dan semua 21 test v3.3 + 14 test v3.4 tetap hijau.

## 11. ADDENDUM — Hotfix Round 4: Kata "Arona" Terlalu Umum di Database Nyata

Teacher melaporkan lewat `main_gui.py`: chat "Aku lagi ngerjain LeadEstate dan Arona." lalu "lanjut yang tadi" membuat Arona mendaftar 5 "kandidat" di note klarifikasi — 1 yang benar (LeadEstate) dan 4 memory afeksi/romantis tak terkait yang cuma kebetulan menyebut nama "Arona" (nama companion sendiri).

**Root cause:** "Arona" bukan stopword bahasa (masih nama project yang sah di skenario lain, dipakai di Test B canonical), tapi di database production Teacher kata itu SANGAT sering muncul (banyak memory afeksi menyebutnya) — mirip bug "yang"/"tadi" v3.3, tapi domain-specific, tidak bisa diselesaikan dengan stopword list statis.

**Perbaikan (2 lapis, `ai/memory_ranking.py` + `ai/companion.py`):**
1. **Frequency-aware scoring** — `score_memory()` sekarang menerima `keyword_frequency` (berapa banyak memory di-match tiap kata, dihitung gratis dari `search_memory()` yang sudah dipanggil, tanpa query tambahan). Kata yang match banyak memory otomatis dapat bobot kecil (analog IDF, murni hitungan, bukan embedding).
2. **Relevance floor di seleksi akhir** (`rank_and_select()`, `MIN_SELECTION_SCORE_RATIO=0.5`) — kandidat yang skornya di bawah 50% skor kandidat #1 dibuang dari SELEKSI AKHIR, bukan cuma dari note. Ini penting karena dengan database kecil (candidate count < budget 10), ranking saja tidak cukup — semua kandidat tetap lolos ke context walau skornya rendah, kalau tidak ada floor yang benar-benar membuang.

Mekanisme note klarifikasi (`_last_recall_scores` + `_REFERENCE_NOTE_SCORE_RATIO=0.6`) sekarang ikut memakai skor yang sudah frequency-aware — jadi 2 lapis threshold: 0.5 di level seleksi konteks, 0.6 (lebih ketat) khusus di level "layak disebut sebagai kandidat klarifikasi".

**Test baru:** T70a/b/c di `test_v3_3_reference_recall.py` mereplikasi PERSIS skenario bug Teacher (memory "Teacher loves Arona", "...berpelukan di atas ranjang", dst sebagai noise) — ketiganya PASS: noise tidak lagi muncul di context maupun note, kandidat asli tetap ada, dan karena cuma ada 1 kandidat kuat, note otomatis pakai varian ringan (tidak memaksa klarifikasi untuk kasus yang sebenarnya jelas).

**Total setelah round 4: 24/24 test v3.3 PASS + 14/14 test v3.4 PASS.**
