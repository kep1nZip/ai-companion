## 3. Keputusan Desain yang Perlu Diketahui Sesi Berikutnya

**Kenapa QTimer polling, bukan Qt signal dari scheduler thread?**
Spec §35-36 merekomendasikan (bukan mewajibkan) signal-based update lewat
worker/UI boundary. Saya pilih polling 1 detik di GUI thread sendiri
(`VisionPage._poll_timer`) yang hanya MEMBACA state thread-safe milik Vision
(`get_mode()`, `companion.current_vision_context()` — keduanya sudah
dilindungi lock) — bukan scheduler yang mendorong update ke GUI. Ini lebih
sederhana, nol risiko cross-thread Qt widget access, dan `VisionAutoScheduler`
tetap 100% tidak tahu GUI ada (Vision Independence Policy §14 utuh: "tidak
import Qt, tidak tahu GUI"). Trade-off: update UI bisa telat sampai 1 detik
dari capture selesai — dianggap dapat diterima untuk background context
refresh (bukan real-time chat).

**Kenapa Manual `refresh()` BLOCKING menunggu lock, bukan skip?**
Spec §17-18 hanya eksplisit menyuruh **Auto** skip (non-blocking) kalau capture
lain sedang jalan — untuk Manual, Teacher secara eksplisit menekan tombol dan
mengharapkan hasil, jadi `refresh()` pakai `with self._capture_lock:` (blocking
acquire). Ini aman karena selalu dipanggil dari `VisionWorker` (QThread
terpisah, bukan GUI thread) — jadi walau menunggu beberapa detik, GUI tetap
responsif. Sudah diverifikasi lewat test `test_no_overlap_manual_vs_auto`.

**Auto capture pertama kali di-set AUTO: langsung capture atau reuse?**
`refresh_if_needed()` dipanggil scheduler SEGERA saat thread start (bukan
nunggu interval dulu) — tapi `refresh_if_needed()` sendiri yang cek freshness
lebih dulu. Kalau context masih fresh (misal baru saja Capture Now manual),
langsung reuse tanpa capture baru. Kalau belum ada/stale, baru capture. Ini
memenuhi §33 dua skenario sekaligus tanpa scheduler perlu tahu bedanya.

## 4. Verifikasi yang SUDAH Dilakukan

Karena sandbox tidak punya PySide6/mss/loguru/google-genai terpasang (tidak
ada akses jaringan untuk install), saya menstub tiga modul tersebut secara
lokal di level `sys.modules` HANYA untuk testing — tidak ada satu baris pun
kode project yang diubah untuk stub ini. `Pillow` asli terpasang jadi
`vision_context.py`/`vision.py` diuji dengan `PIL.Image` sungguhan.

9 test lolos, meng-cover:
1. Default mode = OFF saat instansiasi.
2. OFF memblokir `refresh()` dan `get_context()` (return None).
3. MANUAL: `refresh()` bekerja, `get_context()` mengembalikan hasil.
4. **Known limitation v1.5.1 FIXED**: `set_mode(OFF)` langsung menghapus
   context yang masih fresh — `get_context()` sesudahnya pasti `None`.
5. Auto scheduler capture berkala & stop bersih saat AUTO→MANUAL (thread
   benar-benar berhenti, tidak ada capture lagi setelahnya).
6. **No overlap**: Manual Capture Now menunggu (bukan race) capture Auto yang
   sedang berjalan — dibuktikan lewat elapsed time, bukan asumsi.
7. `shutdown()` menghentikan scheduler dengan bersih (dipanggil dari
   `closeEvent`).
8. `set_mode()` ke mode yang sama itu idempotent — tidak duplikasi thread
   scheduler.
9. Auto scheduler **reuse context fresh**, tidak capture buta tiap interval
   (TTL 30s, interval 0.15s selama 0.6s → cuma 1 capture, bukan ~4).
