## 1. Inspeksi yang Dilakukan Sebelum Implementasi (§5)

Membaca `routine/routine.py`, `routine_engine.py`, `routine_scheduler.py`,
`routine_clock.py`, `routine_event.py`, `routine_history.py`,
`routine_rules.py`, `ai/companion.py`, `developer/routine_debug.py`,
`ui/window.py`, `ui/navigation.py`, `ui/theme.py` SEBELUM menulis kode apa
pun. Temuan penting yang membentuk desain:

- **`RoutineScheduler` bukan thread/background scheduler** — `routine_scheduler.py`
  cuma fungsi murni `current_window(clock)` yang mengklasifikasi jam saat ini
  ke `TimeWindow` (EARLY_MORNING/MORNING/LUNCH/dst). **Tidak ada polling
  loop apa pun di backend Routine.** `Routine.update()`/`evaluate()` HANYA
  dipanggil reaktif dari `Companion.chat()` (lewat Chat/Voice) — kalau
  Teacher tidak chat, Routine tidak pernah re-evaluasi sendiri. Ini beda
  fundamental dari Vision's `VisionAutoScheduler` (v1.5.2) yang punya thread
  background sungguhan.
- **Tidak ada `enable()`/`disable()`/`is_enabled()`** sebelum v1.6 — Routine
  hanya bisa "dimatikan" lewat `Companion(enable_routine=False)` di
  constructor (statis, bukan runtime toggle). Ini persis skenario spec §10
  "If Missing" — jadi saya tambahkan boundary minimal (1 boolean flag +
  3 method) di `Routine`, TANPA redesign apa pun.
- **History HANYA menyimpan event yang SELESAI dipakai** —
  `RoutineHistory.record()` cuma dipanggil dari `Routine.mark_completed()`.
  Event yang di-suppress atau kena cooldown-skip cuma di-`logger.info()`,
  TIDAK PERNAH masuk `_recent` list. Artinya: **mockup spec §9/§42 yang
  menampilkan "⏸ Idle Chat Suppressed" di Recent History TIDAK BISA
  diimplementasikan secara jujur** — backend tidak menyimpan data itu.
  Recent History di GUI HANYA berisi entri ✓ (completed), sesuai §19
  "Do not fabricate."
- **`get_next_schedule()` bukan "jadwal masa depan"** — ia hanya map
  `{event_type: waktu cooldown berakhir}` untuk tipe yang PERNAH trigger.
  Tidak ada konsep "akan trigger jam sekian" di backend sama sekali (sistem
  ini murni reaktif/opportunistic). GUI menampilkan `min()` dari timestamp
  yang backend kembalikan sebagai "Next Eligible" — **bukan** jaminan bahwa
  routine itu akan benar-benar trigger (masih tergantung time-window/idle/
  suppression saat momen itu tiba, logic itu tetap 100% di
  `RoutineEngine.evaluate()`, tidak diduplikasi).
- **Companion sudah punya 4 passthrough Routine** (`get_pending_routine_events`,
  `get_last_routine_event`, `get_next_routine_schedule`, `clear_routine_queue`)
  yang secara eksplisit dikomentari "Developer Panel prep" — pola ini yang
  saya ikuti untuk menambah passthrough baru, BUKAN pola v1.5.2 (yang
  menghindari `Companion` sama sekali dengan meneruskan instance `Vision`
  langsung). Alasan beda pola: `Routine` diinstansiasi **DI DALAM**
  `Companion.__init__` (`self._routine = Routine(...)`), tidak di-inject
  dari `main_gui.py` seperti `Vision` — jadi tidak ada instance `Routine`
  yang bisa diteruskan langsung ke GUI tanpa lewat Companion.

## 3. Keputusan Desain Kunci

**Enable/Disable — tidak ada backlog replay (§12), dibuktikan bukan diasumsikan.**
Karena `evaluate()` cuma mengevaluasi kondisi SAAT DIPANGGIL (bukan antrean
event yang tertunda), `enable()` tidak perlu logic replay-guard sama sekali
— struktur sistem ini SECARA ALAMI tidak punya backlog untuk di-replay. Sudah
diverifikasi test: disable 2× update() (keduanya None), enable(), update()
lagi → tepat SATU event baru (bukan beberapa event menumpuk).

**`update()` di-gate, bukan `poll()`/`get_pending_event()`.** Saat disabled,
`_pending_event` lama (kalau ada) TIDAK dihapus — `disable()` cuma
menghentikan evaluasi BARU. `Companion.chat()` hanya pernah memakai return
value `update()`, jadi behaviour sudah benar tanpa perlu menyentuh getter
lain. Di GUI, section "Current Routine" sengaja disembunyikan (tampil pesan
"Routine is disabled") saat disabled, supaya Teacher tidak salah kira pending
event lama itu masih akan dipakai Companion — ini keputusan presentasi
murni, bukan perubahan behavior backend.

**Suppression Visibility (§20) — best-effort, read-only, tidak mengubah
kontrak evaluate().** `RoutineEngine._last_suppression` di-reset ke `None`
di AWAL setiap `evaluate()` baru, diisi kalau ADA event_type yang kena
suppress dalam pass itu. Ini SIDE-CHANNEL informasional murni — keputusan
suppress 100% masih di `is_suppressed()`, GUI cuma membaca hasil terakhirnya.
Tidak ada "Reason" bertele-tele (spec §20 fallback eksplisit: "If no reason
exists: Status: Suppressed") — saya tampilkan nama `SuppressionLevel` apa
adanya (`Non-casual routines paused` / `All non-critical routines paused`),
BUKAN narasi sebab-akibat yang saya reka sendiri dari `matches_presentation()`/
`matches_focused_work()` (itu bukan bagian dari API contract yang dikembalikan).

**Live update: QTimer polling (1 detik), bukan Qt signal.** Sama seperti
Vision v1.5.2, tapi alasannya beda: Routine backend TIDAK PUNYA thread/timer
apa pun untuk di-signal-kan (Routine Independence Policy — zero Qt import).
Polling di sini **TIDAK PERNAH memanggil `update()`/`evaluate()`** (spec §28:
"Polling must never execute Routine logic") — cuma re-render dari data yang
sudah ada di backend (`get_pending_routine_events()`,
`get_next_routine_schedule()`, `get_routine_history()`, dll — semua getter
murni, tidak ada side effect). Ini memenuhi dua kebutuhan: (1) countdown
cooldown presentation-only tetap jalan real-time (§17), (2) kalau Teacher
chat lewat Chat/Voice page sementara Routine page terbuka, hasilnya ikut
kelihatan tanpa klik Refresh manual.

**Tidak ada `ui/routine_worker.py`.** Semua operasi Routine (enable/disable,
baca history/schedule/suppression) murni in-memory/lokal, tidak ada network
call — dipanggil langsung dari GUI thread, sama seperti pola
`ui/memory_service.py` yang sudah ada (baca sinkron tanpa worker thread).

## 4. Verifikasi yang SUDAH Dilakukan

8 test lolos (di-run 2×, run pertama sempat false-fail karena `__pycache__`
basi dari sebelum edit — sudah dibersihkan dan dikonfirmasi ulang):

1. Default `is_enabled() == True` saat instansiasi.
2. `disable()` → `update()` selalu `None` walau kondisi trigger terpenuhi.
3. `enable()` setelah 2× update() gagal (selagi disabled) → `update()`
   berikutnya langsung dapat SATU event baru, tidak ada backlog menumpuk.
4. History (`get_recent_history()`) tetap utuh sebelum/sesudah disable→enable.
5. `get_next_schedule()` mencerminkan cooldown aktif dari history yang benar.
6. `get_last_suppression()` → `None` kalau tidak ada `vision_context`
   (suppression level otomatis NONE).
7. Pending event yang belum expired TIDAK ditimpa evaluate() baru berulang
   (`update()` dipanggil 2× berturut, hasil identik/`is` sama).
8. `clear_queue()` tidak memengaruhi history sama sekali.

Ditambah: konfirmasi semua 9 method Companion (`is_routine_enabled`,
`enable_routine`, `disable_routine`, `get_routine_history`,
`get_routine_suppression`, + 4 yang sudah ada sebelumnya) benar-benar ada di
kelas `Companion` (lewat `hasattr`, modul Qt/Gemini di-stub minimal untuk
import chain, TIDAK ada kode project yang diubah untuk stub ini).

`diff -rq` terhadap zip asli mengonfirmasi HANYA file yang diizinkan §33
yang tersentuh — nol perubahan di `vision/*` (selain sisa v1.5.2 sebelumnya),
`avatar/*`, `speech/*`, `behavior/*`, `initiative/*`, `database/*`,
