## 1. Inspeksi yang Dilakukan Sebelum Implementasi (§6)

Membaca SEMUA modul `developer/*` (`developer.py`, `behavior_debug.py`,
`vision_debug.py`, `routine_debug.py`, `initiative_debug.py`,
`memory_debug.py`, `avatar_debug.py`, `performance_debug.py`,
`log_viewer.py`), `ai/companion.py`, `ui/window.py`, `ui/settings.py`,
`ui/navigation.py`, `ui/theme.py`, `config/settings.py` SEBELUM menulis kode
apa pun. Temuan penting yang membentuk desain:

- **`DeveloperService` + `DeveloperSnapshot` SUDAH menjadi facade tunggal**
  persis seperti yang diminta spec §17/§18 — `get_snapshot()` membangun SATU
  objek gabungan sekali per render, `export_json()`/`export_markdown()`
  SUDAH ADA. Ini yang saya reuse, BUKAN dibuat ulang.
- **`DeveloperService` sudah diinstansiasi di `ui/window.py`
  (`self._developer_service`) sejak sebelum v1.7**, tapi **belum pernah
  dipakai di GUI mana pun** — tidak ada halaman/dialog yang menampilkannya.
  Artinya **tidak ada "existing developer access pattern" untuk dipertahankan**
  (spec §29) — saya bebas menentukan placement dari nol sesuai §8.
- **`DEVELOPER_MODE` dikonfirmasi ulang TIDAK ADA** di `config/constants.py`
  atau file config manapun — persis seperti catatan v1.4 yang sudah ada di
  docstring `ui/settings.py` ("Developer category SENGAJA tidak ada di
  halaman ini — DEVELOPER_MODE tidak ada di constants.py"). Saya **TIDAK**
  membuat toggle/persistence baru apa pun untuk ini (spec §9 STOP condition
  eksplisit kalau saya nekat bikin).
- **Dua gap data ditemukan** yang membuat mockup spec §10 tidak bisa
  ditampilkan 100% jujur tanpa eskalasi minimal (diizinkan §7):
  1. `VisionSnapshot` **tidak punya field `mode`** (OFF/MANUAL/AUTO dari
     v1.5.2) — `DeveloperService.get_vision()` cuma pernah memanggil
     `companion.current_vision_context()`, tidak pernah menyentuh
     `Vision.get_mode()` sama sekali (bahkan `Companion` sendiri belum
     pernah expose method itu).
  2. `RoutineSnapshot` **tidak punya field `enabled`/`last_suppression`/
     `recent_history_count`** — padahal `Routine.is_enabled()`,
     `Routine.get_last_suppression()`, `Routine.get_recent_history()` semua
     SUDAH ADA sejak v1.6, cuma belum pernah disambungkan ke snapshot
     dataclass ini.
  Keduanya saya tutup dengan **eskalasi minimal** (lihat bagian 2) — bukan
  redesign, murni "plumbing" data yang sudah ada di backend ke tempat yang
  seharusnya, persis skenario yang diizinkan §7: *"If a required value is
  not exposed by a public API... escalate if a minimal read-only API is
  genuinely required."*
- **Tidak ada metric performance "Vision" yang benar-benar tercatat** —
  `Companion._timed()` cuma pernah dipakai untuk `"behavior_update"`,
  `"routine_update"`, `"initiative_update"`, `"gemini"`, `"memory_query"`.
  Mockup spec §10 yang menampilkan "Vision 0.89 s" di Performance **TIDAK
  saya buat** karena datanya tidak ada (§16: "Do not invent measurements").
  Dashboard menampilkan metric APA ADANYA dari `performance.snapshot()`
  dict secara dinamis (bukan daftar nama hardcoded), jadi kalau suatu saat
  Vision timing benar-benar ditambahkan, otomatis muncul tanpa perlu ubah
  GUI lagi.
- **`developer/log_viewer.py` sudah aman untuk di-reuse apa adanya** —
  digrep seluruh codebase, tidak ada satu pun `logger.info/warning/error`
  yang mencatat `GEMINI_API_KEY`/token/secret apa pun. Saya **tidak
  mengubah** `log_viewer.py` sama sekali, cuma mewiring GUI ke
  `DeveloperService.get_logs()` yang sudah ada.

## 3. Keputusan Desain Kunci

**Placement: tombol di Settings, BUKAN item sidebar baru, BUKAN
`DEVELOPER_MODE`.** Karena tidak ada existing access pattern (poin 1) dan
`DEVELOPER_MODE` benar-benar tidak ada, opsi paling minim risiko sesuai §8
adalah "Settings → Developer Tools". Dialog dibuka lewat Signal
(`open_developer_dashboard_requested`) dari tombol di Settings, di-handle di
`ui/window.py` (yang sudah memegang `self._developer_service` sejak
sebelumnya) — TIDAK ADA toggle/config/persistence baru untuk visibility ini.

**Refresh: QTimer 2 detik, presentation-only, TIDAK PERNAH memicu logic.**
Diverifikasi lewat test ketat (`StrictFakeCompanion` yang `raise` kalau
method APAPUN di luar whitelist getter read-only dipanggil) — `get_snapshot()`
dipanggil 5× berturut-turut, nol pemanggilan ke method yang bisa memicu
`Vision.refresh()`/`Routine.update()`/`evaluate()`/`Initiative.evaluate()`/
Memory write. Lihat bagian 4.

**Vision Summary ditampilkan sebagai boolean "Summary available: YES/NO",
BUKAN teks isi summary-nya.** Spec §13 eksplisit mendaftar field itu sebagai
"Summary available" (bukan "Summary content") — saya ikuti literal, supaya
Developer Dashboard tetap murni DIAGNOSTIK (bukan duplikat isi dari Vision
page yang sudah menampilkan summary lengkap).

**Avatar fields ditampilkan apa adanya (`Connection`, `Voice State`,
`Active Layers`), bukan dipecah jadi "Model/Halo/Expression/Lip Sync/Idle
Animation" terpisah seperti mockup §10/§22.** `AvatarSnapshot` yang ada
hanya punya 3 field itu — `active_animation_layers` adalah daftar nama layer
dinamis (frozenset dari `_parameter_layers.keys()`), bukan field bernama
terpisah untuk tiap jenis animasi. Memecahnya jadi field individual berarti
menebak/mengasumsikan struktur yang tidak dijamin API — saya tampilkan
daftar layer apa adanya (§37: "Do not invent state/API").

**Export lewat `QFileDialog.getSaveFileName` (dialog file-save Qt standar),
bukan lokasi tetap.** `export_json()`/`export_markdown()` dipanggil APA
ADANYA (tidak diubah schema-nya sama sekali, §26), hasil string-nya ditulis
ke file yang dipilih Teacher — ini murni I/O file lokal biasa, bukan
persistence/config system baru.

**Log Viewer: reuse murni `DeveloperService.get_logs()`.** Filter
search+level dari GUI diteruskan langsung sebagai parameter ke method yang
sudah ada, tidak ada parsing/logic baru ditambahkan di `log_viewer.py`.
