## 1. Milestone Decision

v2.4 telah selesai dan seluruh Quality Gate terpenuhi.

v2.5 fokus pada masalah memory yang sudah teridentifikasi sejak v2.2:

```text
Memory contradiction / supersession
```

Contoh:

```text
Teacher:
"Aku suka americano."

↓

Memory:
"suka americano"

Teacher:
"Sekarang aku sudah tidak suka americano."

↓

Memory:
"tidak suka americano"
```

Target v2.5 adalah membuat memory memahami bahwa memory baru dapat:

```text
NEW
DUPLICATE
UPDATE
SUPERSEDES
```

bukan sekadar menambah row baru.

---

# 2. Purpose

Target utama:

```text
Teacher statement
      ↓
Memory Extraction
      ↓
Related Existing Memories
      ↓
Relation Detection
      ├── NEW
      ├── DUPLICATE
      ├── UPDATE
      └── SUPERSEDES
      ↓
MemoryManager
      ↓
Current Memory State
```

Tujuan akhir:

```text
Memory should represent
the current coherent state of what is known,
while preserving useful history when practical.
```

---

# 3. Core Principle

Bedakan:

```text
Memory History
```

dengan:

```text
Current Valid Memory
```

Contoh:

```text
History:
"I like americano."
"I no longer like americano."

Current:
"Teacher no longer likes americano."
```

Jangan melakukan destructive deletion tanpa alasan yang jelas.

# 5. Current Root Cause

Saat ini:

```text
MemoryExtractor
```

terutama bekerja terhadap pesan Teacher saat ini.

Sementara:

```text
MemoryManager
```

belum menjadi semantic replacement engine.

Akibatnya:

```text
old fact
+
new contradictory fact
=
two valid-looking rows
```

v2.5 harus membuat hubungan tersebut eksplisit.

# 6. Design Goals

## Goal A — Context-Aware Extraction

Target:

```text
Teacher message
+
related existing memories
→ relation-aware extraction
```

Jangan memberikan seluruh database ke model.

---

## Goal B — Explicit Relation

Minimum relation:

```text
NEW
DUPLICATE
UPDATE
SUPERSEDES
```

Gunakan representation yang konsisten di project.

Jangan menyebarkan magic string bebas ke banyak file.

---

## Goal C — Deterministic Persistence

Setelah relation ditentukan:

```text
NEW
    → create

DUPLICATE
    → no duplicate active memory

UPDATE
    → update appropriate memory

SUPERSEDES
    → old memory becomes inactive/superseded
    → new memory becomes current
```

MemoryExtractor memahami.

MemoryManager menyimpan.

# 8. Phase 1 — Relation Model

### NEW

Tidak ada memory relevan.

```text
"Aku suka teh."
```

→ create.

### DUPLICATE

Informasi substantif sama.

```text
"Aku suka teh."
```

terhadap memory yang sama.

→ jangan membuat duplicate aktif.

### UPDATE

Detail memory yang sama berubah tanpa membalikkan fakta utama.

Contoh:

```text
"Aku sekarang lebih suka americano tanpa gula."
```

terhadap:

```text
"Teacher suka americano."
```

Semantics harus ditentukan dari data nyata.

### SUPERSEDES

Memory baru membatalkan memory lama.

```text
"Aku tidak suka americano lagi."
```

terhadap:

```text
"Teacher suka americano."
```

Expected:

```text
old → superseded
new → active
```

---

# 9. Phase 2 — Related Memory Retrieval

Extractor cukup menerima:

```text
relevant related memories
```

Selection dapat memanfaatkan mekanisme yang sudah ada:

- category,
- keyword/entity overlap,
- existing relevance,
- recency.

Jangan membangun vector search baru kecuali audit membuktikan mekanisme sekarang tidak cukup.

Target:

```text
small context
+
relevant context
=
better semantic decision
```

---

# 10. Phase 3 — Extraction Contract

Output harus tetap machine-readable.

Contoh konseptual:

```json
[
  {
    "category": "preference",
    "content": "Teacher tidak lagi menyukai kopi americano",
    "relation": "SUPERSEDES",
    "target_memory_id": 42
  }
]
```

Contoh tersebut **bukan schema final yang wajib**.

Schema final harus mengikuti project setelah Phase 0.

Prinsip:

```text
Minimum schema change.
Maximum reuse.
```

---

# 11. Phase 4 — Persistence Semantics

MemoryManager menjadi enforcement layer:

```text
Extractor
    ↓
Relation decision
    ↓
MemoryManager
    ↓
Atomic persistence
```

Jangan membuat extractor langsung melakukan SQL update/delete.

---

# 12. Phase 5 — History vs Current State

Preferensi desain:

```text
Old Memory
status = superseded

New Memory
status = active
```

daripada langsung:

```text
DELETE old row
```

jika complexity tetap wajar.

Tujuan:

- traceability,
- debugging,
- future analytics,
- history preservation.

Tetapi jangan menambah lifecycle system besar jika tidak dibutuhkan.

---

# 13. Phase 6 — Contradiction Handling

Primary test:

```text
Aku suka americano.

Sekarang aku tidak suka americano lagi.
```

Expected:

```text
Old preference
    → superseded/inactive

New preference
    → active
```

Forbidden final state:

```text
two active contradictory memories
```

untuk contradiction yang memang sudah didukung oleh relation model.

---

# 14. Phase 7 — Duplicate Handling

Test:

```text
Aku suka americano.
Aku suka americano.
```

Expected:

```text
1 effective active memory
```

Paraphrase:

```text
Aku suka kopi americano.
Aku senang minum americano.
```

Jangan otomatis dianggap duplicate hanya karena wording mirip.

---

# 15. Phase 8 — Update Handling

Contoh:

```text
Aku tinggal di Bandung.

Sekarang aku tinggal di Jakarta.
```

Expected:

```text
Bandung → superseded
Jakarta → active
```

Contoh lain:

```text
Aku kuliah Informatika.

Aku sekarang semester 5.
```

Belum tentu supersession.

Relation harus berdasarkan semantic scope, bukan hanya topic overlap.

# 17. Phase 10 — Async Worker Compatibility

Pertahankan:

```text
MemoryExtractionWorker
```

dan arsitektur asynchronous yang sudah stabil.

Target:

```text
Teacher message
    ↓
Worker
    ↓
Extractor
    ↓
Relation detection
    ↓
MemoryManager
```

Validasi:

- [ ] GUI tidak freeze.
- [ ] Tidak ada duplicate worker.
- [ ] Tidak ada race condition.
- [ ] Tidak ada SQLite locking serius.
- [ ] Shutdown tetap normal.

---

# 18. Ordering / Race Consideration

Karena extraction asynchronous, pastikan:

```text
Message A
Message B
```

yang diproses sebagai:

```text
Task A
Task B
```

tidak menghasilkan state akhir yang mundur.

Worker saat ini serial dan sebaiknya dipertahankan serial selama masih memenuhi kebutuhan.

Jangan menambah concurrency untuk sekadar terlihat lebih cepat.

---

# 19. Data Safety

Sebelum perubahan schema/persistence:

```text
Backup memory.db
```

wajib.

Pengujian awal:

```text
temporary SQLite database
```

bukan database Arona yang sebenarnya.

Tidak boleh melakukan destructive migration tanpa backup.

---

# 20. Migration Principle

Default:

```text
No mass migration.
```

Existing memory tetap valid.

Relation-aware behavior berlaku untuk memory baru.

Migration existing memory hanya boleh dilakukan apabila Phase 0 membuktikan benar-benar diperlukan dan keputusan eksplisit telah dibuat.

# 22. Acceptance Criteria

v2.5 PASS apabila:

- [ ] Explicit facts tetap tersimpan.
- [ ] Noise tetap diabaikan.
- [ ] Hedging protection tetap efektif.
- [ ] Duplicate aktif tidak menumpuk untuk kasus yang didukung.
- [ ] Contradictory active memories tidak lagi hidup berdampingan pada primary contradiction case.
- [ ] Superseded memory dapat diidentifikasi.
- [ ] New memory menjadi current/active.
- [ ] Local provider bekerja.
- [ ] Gemini provider bekerja.
- [ ] Async extraction tetap stabil.
- [ ] GUI tetap responsif.
- [ ] Shutdown tetap normal.
- [ ] Tidak ada regression penting.

---

# 23. Conditional Pass

CONDITIONAL PASS dapat digunakan apabila:

- semantic edge cases tertentu masih ambiguous,
- relation model bekerja untuk kasus utama tetapi belum sempurna pada seluruh paraphrase,
- history retention masih memiliki keterbatasan yang terdokumentasi,
- latency meningkat sedikit tetapi masih acceptable.

Semua limitation harus dicatat eksplisit.

---

# 24. Fail

FAIL apabila:

- Hedging kembali menjadi confirmed memory.
- Explicit fact gagal secara sistematis.
- Primary contradiction masih menghasilkan dua active memory.
- Memory corruption terjadi.
- State menjadi tidak konsisten karena race/order.
- GUI freeze.
- SQLite locking/error serius.
- Provider tertentu membuat pipeline memory crash.
- Silent provider fallback muncul.
