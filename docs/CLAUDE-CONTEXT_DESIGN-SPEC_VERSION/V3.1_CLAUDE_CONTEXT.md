## 3. Apa yang Diimplementasikan (Phase 1-5, 7)

### Item 1+2 — Conversation Continuity + Return-from-Idle
**Root cause (audit):** `idle_seconds` sudah akurat dihitung sejak v2.7, tapi tidak pernah dikirim sebagai sinyal ke model — `_format_time()` cuma menampilkan jam saat ini.
**Fix:** `ai/context_builder.py::categorize_continuity()` — kategorisasi ACTIVE / RETURNING_AFTER_SHORT_GAP / RETURNING_AFTER_LONG_GAP dari `idle_seconds` yang sudah ada. Ambang atas (900s) **sama persis** dengan `IdleRule` yang sudah ada; ambang bawah (60s) satu-satunya angka baru, didokumentasikan eksplisit. Dipakai bareng oleh prompt (`_format_continuity()`) dan Dashboard (Item 5) lewat satu fungsi yang sama — tidak pernah bisa tidak sinkron.

### Item 2 — `ReturningAfterGapRule` (Initiative)
**Root cause:** `RecentInteractionPenaltyRule` (v2.7) memberi penalty flat -20 untuk SEMUA `idle_seconds < 900`, tidak membedakan "baru balas 3 detik lalu" dari "baru kembali 10 menit".
**Fix:** rule baru weight +10 (magnitude terkecil yang sudah dipakai rule lain), aktif khusus zona 60-900 detik. Diverifikasi: kurva skor sekarang -20 → -10 → +20 across 3 zona, sesuai desain.

### Item 3 — Relationship & Prompt Priority (`behavior.txt`)
**Root cause:** v3.0 sudah menambah panduan Relationship/Emotion tapi cuma 2 kutub (rendah/tinggi), urutan prioritas tersirat bukan eksplisit.
**Fix:** tambah 1 kalimat tier menengah relationship + 1 kalimat urutan prioritas eksplisit (task/user intent > emotion/energy > relationship > default style).

### Item 5 — Developer Observability
**Fix:** field `continuity_state` ditambahkan ke `get_personalization_debug_snapshot()`, ditampilkan sebagai "Continuity Signal" (bukan "Applied") — konsisten prinsip v3.0.

**Semua di atas diverifikasi nyata** (bukan cuma compile check): kategorisasi 8 titik ambang, perbandingan skor 3 zona idle via `InitiativeEngine.compute()` langsung, system prompt ter-load dengan teks baru, end-to-end `DeveloperService.get_snapshot()` + `export_markdown()`.

## 4. Item 4 — Auto-Restart (Phase 6): Implementasi + Bug + Fix

### Implementasi Awal
- `ui/window.py::_perform_cleanup()` — diekstrak dari `closeEvent()` (nol perubahan urutan/logic, murni dipindah), dipakai BARENG oleh `closeEvent()` dan restart handler — **tidak diduplikasi**.
- `ui/settings.py::SettingsPage.restart_requested` — Signal baru, pola identik `open_developer_dashboard_requested` yang sudah ada. Di-emit **hanya** kalau salah satu dari 3 blok provider (AI/Memory/Vision) tersimpan — **tidak pernah** untuk perubahan API key sendirian.
- `ui/window.py::_handle_restart_requested()` — QMessageBox informasi → reuse `_perform_cleanup()` → `os.execv(sys.executable, [sys.executable] + sys.argv)`. Dibungkus try/except, gagal = QMessageBox.critical (tidak silent).

**Diverifikasi lewat Qt headless (`QT_QPA_PLATFORM=offscreen`) sebelum diserahkan:** Signal `restart_requested` **0 kali** ter-emit untuk ganti API key sendirian, **1 kali** ter-emit untuk ganti provider — persis requirement yang diminta.

### Bug Ditemukan Teacher (Testing Nyata)
Setelah Apply → restart otomatis berjalan → **model yang aktif masih yang lama**, harus exit manual & jalankan ulang baru benar-benar berubah.

**Root cause dikonfirmasi empiris:** `os.execv()` mewarisi `os.environ` proses lama apa adanya (cuma mengganti kode Python, bukan environment). `AI_PROVIDER=gemini` sudah ter-set ke `os.environ` sebelum restart; setelah `.env` ditulis ulang jadi `local`, proses baru hasil `execv()` **tetap** mewarisi `gemini` di environment-nya. `config/settings.py::load_dotenv()` **tanpa** `override=True` tidak pernah menimpa key yang sudah ada di `os.environ` (perilaku default `python-dotenv`) — jadi nilai lama menang, `.env` baru diabaikan.

**Direproduksi langsung** (simulasi persis skenario ini) — dikonfirmasi 100% sebelum fix diterapkan.

### Fix (v3.1.1)
`config/settings.py`: `load_dotenv()` → `load_dotenv(override=True)`. File `.env` sekarang **selalu** jadi sumber kebenaran final, tidak bisa dikalahkan environment variable yang kebetulan sudah ter-set.

**Diverifikasi ulang:** reproduksi skenario yang sama persis, kali ini dengan `override=True` — hasil benar (`local` menang). Regression check: semua config value (`AI_PROVIDER`, `MEMORY_PROVIDER`, `VISION_PROVIDER`, `CONVERSATION_HISTORY_MAX_MESSAGES`) tetap ter-load normal, semua file yang import `config.settings` tetap compile.

**Satu file yang diubah untuk hotfix ini:** `config/settings.py`.

## 5. Temuan #2 — Conversation Tidak Bertahan Lintas Restart (Diputuskan: Dibiarkan)

**Dilaporkan Teacher:** chat "aku lagi debugging" → keluar-masuk lagi → tanya "tadi aku abis ngapain?" → Arona tidak tahu.

**Diklarifikasi sebagai batas arsitektur yang disengaja, BUKAN bug:**
1. `Conversation` (riwayat chat langsung) cuma hidup selama proses berjalan — tidak pernah disimpan ke disk sejak v1.x. Restart (manual maupun otomatis) memang menghapus riwayat chat — ini realisasi dari batasan yang spec v3.1 sendiri eksplisit larang diubah ("Jangan membuat ConversationManager2, database conversation baru").
2. `Memory` (fakta jangka panjang) seharusnya bertahan, tapi "aku lagi debugging" adalah pernyataan aktivitas kasual — kemungkinan besar terfilter aturan eksplisit `EXTRACTION_SYSTEM_PROMPT`: *"JANGAN simpan basa-basi... obrolan sesaat"*.

**Keputusan Teacher: dibiarkan, dipertimbangkan untuk versi mendatang.** Saya sengaja **tidak** menambal ini dengan persistence baru karena akan melanggar batasan eksplisit spec v3.1. Kalau nanti ingin ditingkatkan, jalur yang sudah ada (penyempurnaan `EXTRACTION_SYSTEM_PROMPT` supaya pernyataan aktivitas lebih reliable tertangkap sebagai memory kategori `project`) adalah opsi kecil dan evidence-based untuk milestone berikutnya — bukan pekerjaan v3.1.
