# 3. v1.9 — Companion Intelligence

## Objective

Make Arona smarter at deciding:

> **Which existing context is actually relevant right now?**

v1.9 is NOT about making Arona more powerful by adding another AI.

It is about using the current systems more intelligently.

# 5. Context Relevance

The primary v1.9 capability is:

> **Relevant context selection.**

Example:

```
```

```
Teacher:
"Arona, kenapa function ini error?"
```

Potentially relevant:

```
```

```
✓ Current conversation
✓ Current Vision
✓ Recent related memory
✓ Current Behavior context
```

Potentially irrelevant:

```
```

```
✗ Old unrelated memories
✗ Unrelated routine history
✗ Stale Vision context
```

The system should avoid sending unnecessary context.

# 7. Relevance Policy

Do NOT invent a completely new AI scoring model unless strictly necessary.

Start with deterministic rules based on existing information.

Potential factors:

```
```

```
Current conversation topic
Vision freshness
Memory query relevance
Routine state
Initiative state
Current user intent
```

Do not use Gemini to decide which context Gemini should receive unless a future specification explicitly calls for it.

# 9. Vision Relevance

Vision context must respect:

```
```

```
OFF
MANUAL

TTL
```

```
```

No Vision context.
```

```
```

```

```
```

```
It may be included when relevant.
```

Do NOT trigger a new Vision capture merely because context relevance is being calculated.

---

# 10. Routine Relevance

Routine is an opportunity source.

The existence of a routine event does not automatically make it relevant to every user question.

Example:

```
```

```
Teacher asks:
"Kenapa Python error?"
```

A lunch reminder is probably irrelevant.

Do not dump all Routine information into Gemini.

---

# 11. Initiative Relevance

Initiative decision information is relevant primarily for autonomous interaction.

For user-initiated conversation:

```
```

```
Initiative
```

may not need to be injected in full.

For autonomous interaction:

```
```

```
Initiative DecisionResult
```

may be highly relevant.

Do not blindly include all Initiative data in every prompt.

---

# 12. ContextBuilder Policy

`ContextBuilder` remains the sole runtime-context assembly boundary.

v1.9 may improve what reaches it.

It must NOT create another context builder.

Correct:

```
```

```
Subsystems
    ↓
Relevance Selection
    ↓
ContextBuilder
    ↓
Gemini
```

If relevance logic belongs naturally inside an existing ContextBuilder boundary, keep it there.

If separation is required, introduce a small explicit component with a single responsibility.

Do not make Companion perform massive context-selection logic inline.

---

# 13. Conversation Relevance

Conversation history is currently shared by normal and autonomous interactions.

v1.9 may improve how much history is considered relevant.

Do NOT create:

```
```

```
AutonomousConversation
ConversationV2
```

without a separate design.

---

# 14. Context Size Policy

Do not send unlimited context.

Potential strategy:

```
```

```
Recent conversation
+
small number of relevant memories
+
fresh Vision
+
current Behavior/Relationship state
```

The exact limits must be derived from the existing implementation and measured behavior.

Do not guess arbitrary limits merely to make a prompt smaller.

---

# 15. Context Priority

If context becomes too large, define deterministic priority.

Potential conceptual priority:

```
```

```
1. Current user message
2. Recent conversation
3. Relevant Vision
4. Relevant Memory
5. Current Behavior
6. Current Relationship
7. Routine/Initiative when relevant
8. Other optional context
```

This is a **design direction**, not an automatic order.

Claude must verify whether it fits the current ContextBuilder architecture before implementing it.

---

# 16. Context Trimming

If trimming is required:

```
```

```
Keep highest-value context.
Remove lowest-value context.
Never silently remove the current user message.
```

Do not truncate randomly.

Do not corrupt Conversation history.

Do not modify the persisted Memory database to reduce prompt size.

# 37. Local / Free Provider

The project goal is to support a free option.

Primary candidate category:

> **Local LLM runtime**

This can remove dependence on cloud quota.

However:

-  exact runtime is NOT decided in this document; 
-  exact model is NOT decided in this document; 
-  hardware compatibility must be assessed before choosing; 
-  latency and memory usage must be measured. 

Do not hard-code a local model yet.

# 39. Free Option Requirements

A free/local provider should ideally support:

-  no mandatory per-message cloud quota; 
-  private/local inference; 
-  Windows compatibility where practical; 
-  integration through a stable local API/runtime; 
-  text generation; 
-  predictable error handling. 

Exact selection requires a later current-market evaluation.

Because model availability changes over time, **do not hard-code a future provider choice in this static roadmap.**
