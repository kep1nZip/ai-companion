# 2. Current v2.1 Memory Architecture

v2.1 changed the timing of Memory Extraction without changing its meaning.

Current conceptual flow:

```text
Teacher
   ↓
Companion.chat()
   ↓
Language generation
   ↓
conversation update
   ↓
schedule memory extraction
   ↓
RETURN reply
```

Background:

```text
Memory Task
   ↓
MemoryExtractor
   ↓
MemoryManager
   ↓
SQLite
```

The important architectural rule established in v2.1:

> **Async changes timing, not meaning.**

`MemoryExtractor` and `MemoryManager` contracts remain stable.

- Companion response latency;

# 7. Do Not Reimplement Memory Extraction Logic

The following remains the responsibility of `MemoryExtractor`:

- deciding whether a message contains useful memory;
- constructing the extraction request;
- interpreting model output;
- determining memory content/category;
- writing through the existing persistence path.

Do not move this logic into:

```text
LocalProvider
GeminiProvider
MemoryWorker
SettingsService
```

Provider only performs provider-specific generation.

# 8. Provider-Agnostic Memory Extraction

Target:

```text

   ┌───┴────┐
   ▼        ▼
```

The extractor should not contain:

```python

```

unless provider differences are genuinely unavoidable and belong at the provider boundary.

Prefer:

```text
MemoryExtractor
   ↓

```

# 12. Model Quality Requirement

Memory Extraction is different from casual chat.

The local model must reliably:

- identify useful facts;
- avoid hallucinating facts;
- avoid inventing memories;
- preserve relevant details;
- obey the extraction format;
- avoid saving irrelevant conversational noise.

A local model producing pleasant chat responses does NOT automatically prove it is safe for Memory Extraction.

---

# 13. Memory Safety Principle

The local model must never cause:

```text
Teacher never said X
        ↓
Memory stores X
```

This is more serious than a stylistic chat difference.

Memory extraction quality must prioritize:

```text
factuality
+
conservative extraction
+
schema compliance
```

over creative response quality.

---

# 14. No Fabricated Memory

Absolute rule:

```text
If uncertain:
    do not create a memory.
```

The model must not infer unsupported facts about Teacher.

Example:

Bad:

```text
Memory: Teacher likes coffee.
```

when Teacher never said so.

Good:

```text
No memory extracted.
```

---

# 17. Background Worker Remains Provider-Agnostic

`MemoryExtractionWorker` should not know:

```text
Gemini
Local
LM Studio
```

It only runs a callable/task.

Provider selection belongs above the worker.

Do not move provider selection into the worker.

---

# 18. Worker Concurrency

v2.1 deliberately uses:

```text
one background worker thread
+
queue
```

to avoid:

- concurrent MemoryExtractor calls;
- duplicate writes;
- unnecessary SQLite concurrency;
- process shutdown problems.

Do NOT increase worker count merely because Local inference is slow.

A single serialized memory extraction worker remains the default.

---

# 19. Local Provider Resource Contention

Current application may use LocalProvider for:

```text
main language generation
```

while Memory Extraction may also use the same local LM Studio instance.

This creates potential resource contention:

```text
Main Chat
     \
      → LM Studio ← Memory Extraction
     /
```

This is one of the primary risks of v2.2.

---

# 20. Resource Coordination

The first implementation should NOT create a second LM Studio process automatically.

Instead, inspect current LocalProvider behavior and test:

```text
Chat generation
+
Background Memory extraction
```

when both target the same LM Studio server.

Measure:

- latency;
- timeouts;
- failed requests;
- queue behavior;
- GPU/VRAM pressure.

---

# 21. Avoid Blocking Main Chat

Even if Local Memory Extraction is slow:

```text
Teacher → reply
```

must not wait.

Example:

```text
Local Chat
10 sec

Memory Extraction
10 sec

User still receives:
~10 sec, not ~20 sec
```

This is a core acceptance criterion.

---

# 22. Memory Queue Backlog

Local inference may be slow enough that messages arrive faster than memory extraction completes.

Example:

```text
Chat 1 → Memory task 1
Chat 2 → Memory task 2
Chat 3 → Memory task 3
...
```

Claude MUST inspect how the queue behaves.

Do not immediately add:

```text
priority queue
 task cancellation
deduplication engine
batching engine
```

unless actual testing demonstrates a need.

---

# 23. Backlog Policy

The existing one-worker queue should remain.

If backlog appears during normal usage:

```text
pending = 1
pending = 2
...
```

record the behavior.

Do not redesign queue semantics during the first implementation.

If backlog becomes a real usability problem:

> document it as a future optimization rather than silently redesigning the system.

---

# 24. Failure Policy

If Local Memory Extraction fails:

```text
Main Chat = SUCCESS
Memory = FAILED
```

The user must still receive the response.

Do not:

```text
turn memory failure into chat failure
```

---

# 25. Retry Policy

v2.2 should NOT introduce aggressive retry.

Recommended:

```text
failure
 ↓
log
 ↓
mark failed
 ↓
continue next task
```

One memory failure must not stop the worker.
